ADR-0001リリース作業の自動化方針

CONTRIBUTING.md に散在しているリリース手順を、役割別 bash スクリプト群 + 共通 lib + RELEASING.md + CI verify ワークフローへと自動化する。ISO/IEC 25010:2023 の品質モデルで優先付けした 4 特性（信頼性・機能適合性・保守性・相互作用性）を根拠とする。

Context

本リポジトリ 9uiLe/plugins のリリース手順は、現状 CONTRIBUTING.md §「バージョンを上げる」と過去のコミット（chore(release): v0.1.1 / PR release/v0.1.1）に分散しており、メンテナーが暗黙知として実行している。手順自体は確立しているが、自動化されていないために以下の問題が顕在化している。

  • 整合性のずれ: v0.1.1 リリース時に marketplace.json の metadata.version と plugins[].version を bump し忘れ、plugin.json との不整合が残存している。
  • 不可逆操作の手作業: タグ作成・git push・gh release create が外部から参照される公開状態を作るが、ヒューマンエラー時の巻き戻し設計がない。
  • 頻度の低さによる記憶劣化: リリースは数週〜数ヶ月に 1 回。次回時に手順を毎度 CONTRIBUTING.md から拾い直すコストが反復する。
  • 仕様ドリフトのリスク: 手順書とコミット履歴が乖離し、誰も気づかないまま「正しい手順」が失われる可能性がある。

これを解消するため、リリース手順のドキュメントとスクリプトを 1 セットで整備し、不可逆境界（git push）の手前で必ず巻き戻せる構造に固める。設計の基礎には ISO/IEC 25010:2023 製品品質モデル（ISO/IEC, 2023）を用い、重点 4 特性で意思決定を駆動した（別途レビュー済み）。

Decision Drivers

  • 信頼性 (Reliability): 途中失敗時にワークツリーが中途半端な状態で残らず、git push 以前なら完全に巻き戻せること（Avizienis et al., 2004; Nygard, 2018）。
  • 機能適合性 (Functional Suitability): 手順上の「やる事」を 1 件も漏らさず、複数 JSON のバージョンを必ず揃え、CHANGELOG の節繰り上げと compare リンク差し替えを決定論的に行えること（Meyer, 1992）。
  • 保守性 (Maintainability): 1 人で半年後に読み返せる粒度。各関数 V(G) ≤ 10、長さ 30 行以内を目安に分割し、shellcheck で機械検証できること（McCabe, 1976; Parnas, 1972）。
  • 相互作用性 (Interaction Capability) — ユーザエラー防止性: 操作頻度が低く誤操作のコストが大きいため、不可逆操作前の確認・--dry-run 既定推奨・引数の厳格バリデーションで誤入力経路を構造的に封じること（Norman, 2013）。
  • 追加依存の最小化: 既存ランタイム依存（bash / git / jq / gh）を超えて Node/Python を導入しない。

Considered Options

Option A — 単一の巨大 bash スクリプト

すべての処理を scripts/release.sh 1 本にまとめる最小構成。引数で prepare / publish / verify を切り替える。

  • Pros: ファイル数が少なく初見の発見性が高い。導入が早い。
  • Cons: McCabe 循環的複雑度が早期に 10 を超え、保守性アンチパターン（モノリシック障害ドメイン相当）に陥る。テストの単位を切り出しにくい。

Option B — 役割別スクリプト + 共通 lib + RELEASING.md + CI verify 推奨

処理を意図単位に分割し、共通の前提チェック・ログ・確認プロンプトを lib/ に集約する。手順の正本は RELEASING.md、整合性ゲートは verify-versions.sh として CI でも再利用する。

リポジトリ追加ファイル tree 
RELEASING.md                       # 手順の正本
scripts/
  lib/
    common.sh                      # ログ・前提チェック・dry-run・確認プロンプト
    version.sh                     # plugin.json / marketplace.json の整合更新
    changelog.sh                   # CHANGELOG セクション繰り上げ・compare リンク
    release-notes.sh               # releases/vX.Y.Z.md 雛形生成
  release-prepare.sh               # ブランチ → 編集 → コミット → PR
  release-publish.sh               # master 取得 → tag → GH Release
  verify-versions.sh               # 整合性ゲート（CI でも使う）
.github/workflows/
  verify-versions.yml              # PR ごとに verify-versions.sh を実行
  • Pros: 責務分離により V(G) を低く保てる。verify-versions.sh を CI と本処理の双方から呼べる（事後条件アサーション）。bash 完結で新規ランタイム依存ゼロ。
  • Cons: ファイル数が増え、初見の見渡しコストがわずかに上がる。共通 lib の引数規約を最初に決めておく必要がある。

Option C — Node.js / Python による専用 CLI

型安全な言語で専用 CLI を新規実装する。commander / click 等で引数を厳格化し、JSON 編集も AST ベースで行う。

  • Pros: 引数バリデーション・テスト・型整合が言語側でほぼ自動。
  • Cons: 本リポジトリに Node/Python の既存依存はない。リリース自動化のためだけにランタイムを足すのは機能適合性の「ゴールドプレーティング」（過剰設計）に該当（ISO/IEC 25010:2023 §機能適合性 §5 アンチパターン）。

Decision

✓

採用: Option B — 役割別 bash スクリプト + 共通 lib + RELEASING.md + CI verify

4 つの重点品質特性すべてで A・C を上回る。とくに「依存最小化」と「保守性」を同時に満たせる唯一の案であり、本リポジトリの規模（メンテナー 1〜数名、リリース頻度数週〜数ヶ月）と整合する。verify-versions.sh を本処理と CI の双方から呼び出すことで、Design by Contract（Meyer, 1992）における事後条件アサーションを実装レベルで保証する。

採用タクティクスの内訳

重点特性 採用タクティクス 根拠
信頼性 set -euo pipefail + trap ERR INT による自動 git restore + 一時ディレクトリでの加工 → 全成功時のみ mv で原子的反映 + --dry-run 既定推奨 Fail-Fast (§信頼性 §3.3); 冪等性・チェックポイント (§信頼性 §2.4); 段階的ロールアウト相当 (§信頼性 §2.1)
機能適合性 RELEASING.md 内の簡易 RTM で手順とスクリプト関数を双方向リンク + 各処理末尾で verify-versions.sh を事後条件として呼び出し + awk で CHANGELOG パースを 3 ステップに分解 RTM (Gotel & Finkelstein, 1994); Design by Contract (Meyer, 1992); 仕様駆動テスト (ISO/IEC/IEEE 29119-4:2021)
保守性 lib を version.sh / changelog.sh / release-notes.sh / common.sh に責務分離（循環依存ゼロ） + shellcheck を CI 必須 + 構造化ログ [release-prepare] [INFO] ... 情報隠蔽 (Parnas, 1972); 構造化設計 (Stevens et al., 1974); V(G) ≤ 10 目標 (McCabe, 1976)
相互作用性 不可逆操作前にバージョン文字列の再入力（タイプ確認）= 強制機能 + --check で副作用なしの事前バリデーション + エラーメッセージに必ず次の手を併記 Forcing Function (Norman, 2013); ユーザエラー防止性 (§相互作用性 §2.4); エラー回復導線 (Nielsen, 1993)

Consequences

Positive

  • リリース時の手作業項目が「PR レビュー」「マージ判断」「ローカル動作確認」の 3 点に縮約される。
  • バージョン整合性が CI で機械的にゲートされ、v0.1.1 で発生したような bump 漏れが構造的に再発しない。
  • git push 以前は何度失敗しても git restore で初期状態に戻るため、リリース作業の心理的負荷が下がる。
  • RELEASING.md がドキュメント・スクリプト・CI 設定を結ぶ正本となり、仕様ドリフトを抑止できる。

Negative

  • 追加ファイルが 8 つ（スクリプト 4 + lib 4 + ワークフロー 1 + 手順書 1）増え、初見の見渡しコストが上がる。RELEASING.md 冒頭の俯瞰図で補う。
  • bash の引数バリデーションは Node/Python に比べ表現力が低く、SemVer 正規表現や JSON 編集の不変条件を jq と関数規約で人手担保する必要がある。
  • CHANGELOG の Keep a Changelog 形式から外れた書き方をすると awk パースが abort する（意図的な厳格性だが、未経験者には驚きとなる）。

Neutral

  • GitHub Release の本文公開（gh release create）は手動のままとする。不可逆操作の自動化はユーザエラー防止性を毀損する判断（Norman, 2013）。
  • 2 プラグイン同時リリース・pre-release（rc）対応は本 ADR のスコープ外。必要時に別 ADR で再検討。

Compliance & Monitoring

  • CI ゲート: .github/workflows/verify-versions.yml が PR ごとに verify-versions.sh を実行し、plugin.json と marketplace.json.plugins[].version の一致を強制する。
  • 静的検査: 同ワークフロー内で shellcheck を scripts/**/*.sh に対して実行し、warning 0 件を必須化する。
  • 受け入れ検証: リリース時に 3 ケースの誤入力（不正バージョン・clean でないワークツリー・既存 tag）を意図的に試し、すべて状態変更ゼロで abort することを目視確認する（カオス的検証, Basiri et al., 2016 の縮小適用）。
  • 仕様ドリフト防止: RELEASING.md ・スクリプト・verify-versions.yml を同一 PR で更新するルールを CONTRIBUTING.md に追記する（§機能適合性 §5 アンチパターン「仕様ドリフト」対策）。
