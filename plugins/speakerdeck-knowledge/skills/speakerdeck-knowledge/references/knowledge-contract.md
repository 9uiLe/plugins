# 実務へ転換する知識の設計

知識の単位は「どの状況で何を判断し、どう動き、どう確かめるか」とする。スライドの掲載順に依存せず、実務上の問いで構成する。主要知識に安定した ID（例 `K01`）を付け、Markdown と HTML で共通に使う。

## 知識ごとに記載する情報

| 要素 | 内容 |
| --- | --- |
| 判断基準 | 選ぶ行動、避ける行動と、その判断理由 |
| 根拠 | 著者の説明・比較事例・画像観察と該当ページ |
| 仕組み | 効果を期待する理由。原資料の説明と独自の推論を区別 |
| 適用条件 | 対象利用者、利用状態、必要な前提 |
| 作業 | 必要な入力、変更対象、実行手順や実装方針 |
| 具体例 | 条件と行動の対応を説明する例。独自の例は応用提案と表示 |
| 検証 | 観察可能な結果、失敗の兆候、確認方法 |
| 限界 | 反例、使わない状況、原資料が説明していないこと |

根拠は「原資料」「画像観察」「応用提案」の表示で追えるようにする。数値・引用・因果主張には出典を近接させる。資料にない理由や効果を補う場合は推論と記し、未説明の事項を体裁のために創作しない。具体例は理解に必要な場合に置く。

## 資料の構成

入口に資料名、読者、目的、使う場面、出典（タイトル・著者・公開日・URL・取得日）を記載する。用語は初出で定義する。知識の関係や使う順序を全体像として示し、各知識の適用へ進む。

実践例では、具体的な入力から判断、作業、検証までを通して説明する。ユーザーの対象が不明なら架空の対象と明示する。最後に AI への作業指示と読解範囲・限界を記載する。本文の全ての文が、資料内の前提・用語・節参照だけで意味を持つように書く。

## AI への作業指示

AI が次の作業を特定できるよう、次を具体化する。

1. 目的・対象・対象外と、必要な入力（リポジトリ、利用者、既存仕様など）。
2. 適用する知識 ID と条件、優先順位の判断基準。
3. 調査、判断、変更、検証の作業順。未確認の API やファイルは調査対象として扱う。
4. 受入条件、回帰確認、判断できない場合の停止・相談条件。
5. 報告する変更理由、知識との対応、検証結果、未解決事項。

一般例でも作業順と確認方法を完成させ、実案件で確定する入力は区別する。抽出の依頼は実装やデプロイの許可を含まない。受入条件は適用先の要件に従う。共有 HTML の PC 専用という閲覧条件と、適用先システムの対応端末は別に定める。

## 完了条件

各知識から行動を選べ、別の業務へ移すときに維持する原則と確認すべき前提が分かること。根拠ページが主張を支え、提案と原資料が区別されていること。原図を根拠とする判断には、観察箇所と意味を記載すること。

Markdown を知識の正本として HTML と照合する。具体的な条件、作業、例外、不確実性、AI 指示を保持する。会話の参照や制作過程の説明は成果物の理解に必要な情報に置き換える。検証手順の記載と、実際にその効果を確認した結果は区別する。
