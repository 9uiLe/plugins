# UI の知識を画面改善へつなげる実践ガイド

この資料は、デザイナー・エンジニア・プロダクト担当者が、利用者の迷いを診断し、変更理由と検証方法を揃えるために使う。UI は利用者が情報を読み、操作する接点を指す。既存画面のレビュー、新機能の設計、AI への実装依頼で利用できる。

出典: 原 佑一『[いいUIとは？初心者向けに事例をもとにUIデザインを分解](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai)』、2026-08-29 公開。2026-09-08 取得、全30ページ。

**根拠の区分:** 「原資料」は講演の内容を短く言い換えたもの。「画像観察」は図から確認した事項。「応用提案」は本資料で追加した実務上の判断・手順・検証案であり、講演者の推奨や実証結果ではない。

実践例には、初めて経費申請する社員の確認画面を用いる。経費申請とは、支出の用途・金額・領収書を登録し、承認に必要な情報を提出する手続きとして扱う。例の仕様と改善案は本資料の独自提案であり、適用時には実際の社内規定を確認する。

## 改善の全体像

本資料で提案する進め方は、利用者の到達目標を決め、操作上の障害を除き、実際の成果と伝わり方を確認すること。検証で目標との不一致が見つかったら、見た目だけを調整せず、機能の必要性まで戻って考える。

1. **利用者と目標を定める（K04・K06）:** 誰に、どんな変化を届けたいかを決める。
2. **操作上の障害を除く（K01〜K03）:** 操作を見つけ、結果を予測し、次回に経験を使えるようにする。
3. **成果と伝わり方を確かめる（K04〜K06）:** 仕事への効果と、利用者が受け取る意味を別々に確かめる。

目標と結果が一致しなければ、目標・機能・画面の対応を見直す。

## K01 — 操作の意味と、その操作が必要な時点を揃える

**原資料:** 支払い画面の改善例は、選択肢を具体化し、カード挿入を次の段階で案内する。[p.7–8](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=8)

**画像観察:** 左の画面で支払い方法を選び、右の画面でカードを挿入します。選択肢の言葉とアイコン、二つの画面の間の矢印に注目してください。操作の意味だけでなく、案内するタイミングも設計対象です。

**応用提案:** 質問の解読とボタンの意味の推測を同時に要求すると、利用者は説明文を往復して判断することになると考えられる。入力フォームでは状態とアクションを対応させる。

- **条件:** 分岐や複数段階を持ち、何を押すか・いつ入力するかで迷う画面。
- **作業:** 各状態の目的、必要入力、次の状態を書き出す。ボタン名に行為と対象を含め、次段階の詳しい操作は必要になる時点に配置する。アイコンは文字と組み合わせ、意味が伝わるか確認する。
- **例:** 経費入力の次が確認画面なら「申請内容を確認」、提出が発生するなら「経費を申請」と分ける。
- **検証:** 押す前に利用者へ遷移先と保存・提出の有無を説明してもらい、実際の挙動と照合する。
- **限界:** 料金や不可逆な結果など、選択前に必要な条件は後段に隠さない。画面を細分化すること自体を目標にしない。

## K02 — 確認する情報から、主な操作へ視線を導く

**原資料:** 発券例は金額確認と操作の順序、ボタンの強弱を見直している。[p.9–12](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=12)

**画像観察:** 金額のまとまりがボタンより上にあり、右下の発券は塗りつぶし、取消は枠線です。「確認してから操作する」という順序と、主な操作の強弱を同じ画面で読み取れます。

**応用提案:** 判断材料が操作の後に現れる配置では、読み飛ばしや戻りが起きやすいと考えられる。情報の順序を実際の判断順へ寄せる。

- **条件:** 確認後に確定する画面、複数のボタンが同程度に目立つ画面。
- **作業:** 確定前に必要な項目を洗い出し、確定操作より先に読む順序へ配置する。主要操作と補助操作を区別し、既存のコンポーネント・配色・フォーカス順を使って実装する。
- **例:** 経費の合計、用途、添付状況を示した後に申請操作を置く。説明文を削る前に、項目名だけで意味が通るか確かめる。
- **検証:** 読み順、Tab 移動順、必要項目の発見、編集へ戻る操作を確認する。
- **限界:** 「確定は常に右」を普遍則にしない。対象言語、OS の慣習、狭い画面を考慮する。削除など影響の大きい操作を無条件に強調しない。

## K03 — 覚えた操作の規則を、別の画面でも使えるようにする

**原資料:** 講演では発見・予測・学習を設計の観点として紹介する。[p.13–16](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=13)

**画像観察:** p.13 は三原則を山幡氏の定義として紹介している。p.16 の二つの確認画面は、主要操作の位置と強調が共通している。[p.16](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=16)

**応用提案:** 規則を共有すると、一度得た操作経験を次の場面へ移しやすいと考えられる。

- **条件:** 同じ目的の操作が複数画面に存在する。
- **作業:** ボタンの行為、名前、位置、強調、戻り先を一覧化する。同じ意味を既存コンポーネントに揃え、意味が違う操作は名前で区別する。
- **例:** 下書きの保存と申請の提出を両方「OK」に統一しない。同じ申請操作は画面ごとに別の呼称へ変えない。
- **検証:** 最初の画面で操作を覚えた利用者が、別画面でも説明なしで目的を達成できるか観察する。
- **限界:** 見た目の一貫性で、異なる結果を同じ操作に見せない。原資料にある「OK」の表記を全ボタンへの推奨と解釈しない。

## K04 — 操作の成立と、利用者の成果を別々に確認する

**原資料:** 機能の使いやすさに加えて、利用者への価値とサービスらしさを検討する枠組みが提示される。[p.18–21](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=20)

**画像観察:** 立体図の下に機能、その上に価値とブランドが置かれています。左の囲みが強調するのは価値とブランドです。操作が成立した後も、何を届けるかを検討する構造として読めます。

**応用提案:** 機能が使えても、解く問題を間違えていれば業務成果は変わらない。評価を三つの問いへ分ける。

| 評価するもの | 経費申請での問い | 確認のしかた |
| --- | --- | --- |
| 操作 | 必要事項を入力して提出できるか | タスク観察、エラー・やり直しの記録 |
| 成果 | 必要な情報が揃い、差し戻しを避けられるか | 差し戻し理由の分類、申請者と承認者への確認 |
| 伝わり方 | 手続きに不慣れでも安心して進めるか | 文言をどう受け取ったか聞き、困惑を記録 |

- **条件:** 機能が動くことだけで完成を判断している設計・レビュー。
- **作業:** 対象者、困りごと、望ましい変化を一文にし、操作テストと成果検証を分ける。
- **検証:** 技術テストだけで「不安が減る」「効率が上がる」と報告しない。成果をまだ調べていなければ未検証とする。
- **限界:** 講演の枠組みは品質の全項目を網羅する規格ではない。性能・セキュリティ・アクセシビリティの既存要件は別途維持する。

## K05 — サービスの姿勢を、利用者の状況に合う言葉へ変える

**原資料:** Duolingo と Ameba の事例は、表現のトーンと利用者の体験を結び付けて説明される。[p.22–23](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=22)

**応用提案:** トーンは文言の調子や態度を指す。成功・失敗・未入力など利用者の状態に応じて、サービスの姿勢を具体的な表現へ翻訳する。

- **条件:** エラー、完了、通知、初回利用など、感情と行動の両方を扱う場面。
- **作業:** ブランド方針と利用者の不安を確認し、望む態度と避けたい表現を決める。責める文言を、状態・回復手順・入力の保持状況へ書き換える。
- **例:** 「入力が不正です」から「領収書を追加すると申請できます」へ。ただし実際に添付不足が原因の場合に限る。通信障害を入力ミスと説明しない。
- **検証:** 文言の好みだけでなく、原因と次の操作を理解できるか、利用者が責められたと感じないか確認する。
- **限界:** 他社の褒め方や通知頻度をそのまま移植しない。資料内の事例は著者の観察であり、継続率への因果効果を示す実験ではない。

## K06 — 機能から望む体験までのつながりを、検証可能な仮説にする

**原資料:** 就活向けカレンダーの例は、機能・便益・価値・体験を段階で結んでいる。[p.25–29](https://speakerdeck.com/yuichi_hara7/ii-ui-toha-shoshinshamuke-ni-jirei-o-moto-ni-ui-dezain-o-bunkai?slide=29)

**画像観察:** 中央は機能から体験へ段階をたどり、左の長い矢印は機能と体験全体を結んでいます。各段階の違いを見た上で、自分の機能がどんな体験につながるかを考えます。図は効果の実証ではありません。

**応用提案:** 便益は直接の助け、価値はその人にとって意味のある変化、体験は利用を通じた感じ方や行動全体として区別する。矢印ごとに、成立条件と反証を置く。

| 段階 | 経費申請での仮説 | 成立しない例 |
| --- | --- | --- |
| 機能 | 領収書と用途を登録できる | 添付が完了しても保存されない |
| 便益 | 提出前に不足を見つけられる | チェックが社内規定と一致しない |
| 価値 | 差し戻しの対応を減らせる | 差し戻しの主因が別の承認規則にある |
| 体験 | 見通しを持って申請できる | 完了後の状態が分からず問い合わせる |

- **条件:** 機能の追加理由や期待効果を説明する場面。
- **作業:** 機能から体験まで記述し、各矢印の前提を確認する。目指す体験から逆にたどり、不要な機能・欠けた情報を探す。
- **検証:** 不足検出は規定に基づくケースで確認し、差し戻しや見通しへの効果は実際の利用で別に調べる。
- **限界:** 機能の追加だけで価値や体験が保証されるとは扱わない。数値目標は現状値と業務上の必要性を確認して決める。

## 実践例 — 社内経費申請の確認画面を改善する

**架空の応用例:** 初めて経費申請する社員の確認画面を対象に、K01〜K06 を適用する。

**入力条件:** 初めて経費申請する社員が対象。確認画面の冒頭に「はい／いいえ」があり、下部に金額が表示されていると仮定する。「はい」が提出なのか次画面なのかは、実装を調べるまで未確定。

1. **調査:** 画面からイベント処理、保存・提出 API、バリデーション、失敗時の表示をたどる。提出の意味と社内規定を確認する。原資料から規定を推測しない。
2. **診断:** 行為が不明なら K01、判断材料が操作の後にあるなら K02、他画面と意味が揃わなければ K03 を適用する。
3. **変更:** 合計・用途・添付状況を先に示す。確認へ進む操作と提出を名前で区別する。編集へ戻る道を保ち、エラーは原因と回復方法を表示する（K05）。既存の状態管理とコンポーネントを再利用する。
4. **挙動の確認:** 下書き、確認、提出中、成功、失敗を追う。提出中の再操作、失敗時の入力保持、添付不足、編集後の再確認を検証する。重複提出の防止は既存 API の保証も調べる。
5. **成果の確認:** 新規利用者が操作の結果を予測できるか観察し、差し戻し理由と提出後の問い合わせを調べる（K04・K06）。結果がなければ成果は未検証と報告する。

## AI へ渡す作業指示

この節と本文を一緒に渡す。対象プロジェクトと実装の許可は、依頼者が別途指定する。

```text
目的: 指定された経費申請画面で、操作の意味と必要情報を理解して提出できるようにする。
根拠: この資料の K01〜K06。原資料と応用提案を区別する。

必要な入力:
- 対象リポジトリ・画面、利用者、変更可能な範囲。
- 申請規定、保存と提出の違い、既存コンポーネント・文言方針。
- 現在の問題の証拠。ない場合は仮説として記録する。

作業:
1. 画面・イベント・API・テストを調べ、状態と遷移を一覧にする。
2. 各問題を知識 ID に対応付け、変更理由と受入条件を書く。
3. 行為が伝わる文言、確認情報の順序、一貫した操作、回復案内を実装する。
4. 実際の変更に対応する既存テストと必要な挙動テストを実行する。
5. 初回操作・再利用時の理解、業務成果を確認する方法を示す。

受入条件:
- ボタンが示す行為と実際の遷移・送信が一致する。
- 確定前に必要情報を確認でき、編集へ戻れる。
- 失敗時に次の行動が分かり、既存の入力保持・重複防止を壊さない。
- キーボード・狭い画面・既存のアクセシビリティ要件で回帰がない。
- 不安軽減や差し戻し削減は、観測できた場合だけ成果として報告する。

停止・相談条件:
- 保存と提出の意味、規定、権限が不明で振る舞いを確定できない。
- 変更に API 契約や承認フローの変更が必要だが、許可範囲が不明。
それまでの調査と独立して進められる作業を残し、未決事項を具体的に伝える。

対象外: 無断の規定変更、ブランド刷新、公開・デプロイ、実データの申請。
報告: 変更箇所、知識 ID と理由、検証結果、未検証の成果、残る判断。
```
