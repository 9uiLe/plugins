DESIGN HARNESS / KNOWLEDGE & PRACTICE

AI が生成する画面の妥当性を、
チームで確かめる

デザイナー・エンジニア・プロダクト担当者が、AI に渡す設計条件と、生成後の検査・人の判断を整えるための実践ガイド。既存プロダクトの定型画面を複数人で開発し、レビュー待ちや同じ指摘の繰り返しが起きる場面で使う。

使う場面
定型画面の生成・レビュー体制の整備・AI への実装依頼
用語
デザインハーネスは、設計の判断材料と検証の仕組みを AI が利用できるよう整える考え方。制約は守る規則、コンテキストは業務の目的・利用者・状態などの文脈を指す。デザイントークンは色や余白等に付けた共通の名前と値、設計契約は使える部品や条件の約束、lint は規則違反を検出する検査、CI は変更時に検査を実行する仕組みとして扱う。

K01

生成を増やす前に、判断の責任と待ちを明らかにする

使う場面複数の開発者が AI で画面を作り、レビューが一人に集中しているとき。

原資料 講演は、生成速度と判断体制の不均衡を組織上の課題として扱う。 p.4 / p.5 / p.6 / p.7 / p.9 / p.31 / p.32

実務への適用 応用提案

処理できる量と、承認すべき人が不明な問題を分けて扱う。前者には作業の切り分け、後者には決定権と判断材料の明示が必要になる。

作業
直近のレビューについて、依頼時刻・初回判断時刻・指摘内容・最終判断者を記録する。指摘を、既存規則の違反、業務文脈の不足、新しい判断の三つに分類する。各分類について、検査の担当、修正の担当、最終判断者、相談先を決める。
具体例
担当者フィルターでは、部品の契約適合をエンジニア、表示範囲の業務上の妥当性を業務担当、情報の理解しやすさをデザイナーが確認する案を置く。最終責任者は対象チームが合意して決める。
検証
待ち時間と実際のレビュー時間を別々に記録し、規則違反が人に届く件数と、判断者未定で止まる件数を追う。改善前後で依頼量と難易度が違う場合は、その差も記載する。
適用の限界
人数を増やす必要性を否定する指針ではない。決定権や優先順位が未整理のまま検査を増やしても、承認待ちは解消しない。
K02

小さな設計契約を、検査できる形で渡す

使う場面既存の部品・トークン・画面パターンがあり、守るべき選択肢を定義できるとき。

原資料 講演は、生成時に守る型を明示することを提案する。 p.19 / p.25 / p.26

実務への適用 応用提案

規則を「よい画面にする」という形容ではなく、対象・条件・許される値・確認方法の組にする。生成と検査が同じ契約を参照すれば、判断の食い違いを追いやすくなる。

規則の要素担当者フィルターの例
対象と条件既存の顧客一覧にフィルターを追加する場合
許される実装承認済み選択部品とデザイントークンを使用
証拠部品の利用箇所、描画結果、操作結果
例外と責任契約に必要な状態がなければ管理者へ相談
作業
繰り返し起きた逸脱から小さく始め、各規則に ID、目的、適用範囲、例外、検査方法、管理者を付ける。承認済み部品の参照先を入口にまとめ、実装と検査の両方から参照できる状態にする。
具体例
DH-C01「担当者を選ぶ入力は既存の承認済み選択部品を使う」。実際に画面へ配置され、ラベル・値・変更イベントが既存契約に従うことを確かめる。import の有無だけで合格としない。
検証
規則を守る画面と、一箇所だけ違反する画面で検査が区別できることを確認する。例外を認める場合は理由と範囲を記録し、全画面を除外する設定にしない。
適用の限界
規則数や行数は品質指標ではない。判断に使われない規則、検査できない曖昧な規則、互いに矛盾する規則を増やすと運用が難しくなる。
K03

業務文脈を ID で参照し、必要な分だけ読み込む

使う場面見た目は既存画面に似ていても、対象者・権限・状態・業務の順序が異なるとき。

原資料 講演は、業務に必要な情報を参照可能な単位で渡す構成を示す。 p.20 / p.25

実務への適用 応用提案

長期的に共通する部品契約と、変更されやすい画面の文脈を分ける。AI が使った根拠と版を残すことで、古い仕様による誤実装を調査できる。

参照 ID（応用例）内容配置例
DH-INDEX設計情報への入口DESIGN.md
DH-C01承認済み入力部品の契約docs/design/contracts.md
DH-X01顧客一覧の対象者・権限・目的docs/design/customer-list.md
DH-S01フィルターの状態と遷移docs/design/filter-states.md
作業
設計の入口ファイルに、規則、部品、画面例、業務状態の ID と参照先を並べる。依頼ごとに必要な ID を選び、参照が解決できるか確認する。対象者、目的、権限、入力、空・読込中・失敗・成功の状態を具体化し、仕様変更時の更新担当を決める。
具体例
以下の配置は新規に作る場合の例であり、実在するパスではない。既存の設計文書がある場合は、その入口と管理方法を使う。担当者フィルターの依頼には対象画面と状態定義を渡し、無関係な全画面の資料は読み込ませない。
検証
選んだ ID が全て参照先へ解決でき、部品契約と画面仕様の版が矛盾しないことを確認する。AI に入力と状態の対応を説明させ、実際の業務仕様と照合する。
適用の限界
ファイル名が DESIGN.md であることだけで、自動的に読み込まれるとは限らない。使うエージェントへの参照指示が必要。ID があっても、誤った内容や古い状態定義は防げない。
K04

機械の判定と、人に残すレビューを分ける

使う場面同じ規則を何度も人が確認している一方、画面の意図や業務上の自然さは機械だけでは決められないとき。

原資料 講演は、検査結果に人の確認が必要な区分を設ける。 p.10 / p.21 / p.26 / p.27 / p.28

図で見る箇所

画面から複数の検査観点へ線が分かれ、下の結果へ集まる。左の説明では、人が見る結果と AI に修正を返す結果が区別されている。全ての観点を一つの自動合否に押し込まない構成を読み取る。

実務への適用 応用提案

機械が観測できる事実と、人が文脈から決める妥当性を分ける。合格は検査対象の条件を満たしたことを意味し、画面全体の承認とは区別する。

結果意味次の作業
合格実行した検査の条件を満たした人が残りの判断を確認する
失敗期待値と観測値が不一致AI が修正し、同じ条件で再検査する
レビュー意図や業務文脈を人が判断する根拠と所見を担当者へ渡す
未検証（応用提案）実行できない、または証拠が不足理由を記録し、合格扱いを避ける
作業
規則ごとに静的検査、描画・操作検査、人のレビューを割り当てる。検査結果には規則 ID、対象画面と状態、実行環境、期待値、観測値、証拠を残す。検査不能・未実行は合格へ変換せず、理由付きの未検証として扱う。明確な違反は AI へ返して修正し、再検査する。
具体例
承認済み部品の利用はコードと描画で確認する。空結果の案内と再操作は状態を作って確認する。フィルター名が業務担当者に伝わるかは、人のレビューに残す。AI の画面所見は判断材料として添える。
検証
意図的に壊した実装が失敗し、修正後に合格へ変わることを確認する。判定不能の入力で合格が出ないこと、人がレビュー項目へ到達できることも確認する。
適用の限界
スクリーンショットだけでは操作や権限を検証できない。p.25 のデモ結果は例示であり、別の製品で同じ改善率や完全な品質保証を得る証拠にはならない。
K05

レビューの理由を、次回の契約と検査に戻す

使う場面修正したはずの問題が別の画面や次の生成で繰り返されるとき。

原資料 講演は、レビュー結果を以後の生成条件に戻す循環を示す。 p.22 / p.27 / p.31

図で見る箇所

上側の流れは修正から記録、制約更新、次の生成へ進み、下側の線が再びレビューへ戻る。単発の画面修正で終わらず、次の生成が同じ判断を利用する関係に注目する。

実務への適用 応用提案

一回の指摘をそのまま全画面の禁止事項へ昇格させず、再利用できる条件と理由を取り出す。例外と更新責任を残すと、規則の肥大化や陳腐化を見直せる。

作業
レビュー記録に、対象、状態、現象、理由、決定者、適用範囲、例外、関連規則を残す。繰り返しに使う判断なら契約を更新し、対応する検査または人が見る観点も更新する。次の生成で規則が参照され、同じ問題を検出できるか確認する。
具体例
「検索結果が空なら再試行を出す」という指摘を一律に採用しない。条件不一致による空結果ならフィルター解除、通信失敗なら再試行と分け、DH-S01 の状態定義と検査へ戻す。
検証
保存した再現条件で旧実装の問題を検出でき、修正後に解消することを確かめる。別の状態で誤検出しないことを確認し、次の依頼に更新版が渡ることも追う。
適用の限界
好みの指摘や一画面だけの都合を共通規則にしない。更新担当・判断者・見直しの契機がなければ、記録が増えても運用は改善しない。
K06

既存の型がある範囲から導入し、探索の判断を残す

使う場面デザインハーネスの導入範囲と、最初に確かめる効果を決めるとき。

原資料 講演は、既存の型を使う開発と、正解を探す活動の適性を分ける。 p.30 / p.31 / p.32 / p.33

実務への適用 応用提案

合意済みの基準を再利用する作業から始めると、検査の妥当性と運用負担を観測しやすい。基準そのものを作る探索では、仮説と学習結果を人が判断する場を用意する。

作業
一つの定型画面と代表的な変更を選び、必要な規則だけで試す。レビュー待ち、繰り返し指摘、検査の誤検出、保守時間を記録する。ルールの追加は観測した問題と結び付け、目的に合わない場合は適用範囲や規則を見直す。
具体例
顧客一覧への担当者フィルター追加で試行する。顧客管理そのものの価値提案や、未知の利用者向けの新体験を決める判断は、自動検査の合格条件に置き換えない。
検証
条件の近い変更で、導入前後の待ち時間・再指摘・誤検出・保守負担を比較する。差が出なければ成功とせず、規則、業務文脈、担当範囲のどこが不足しているか調べる。
適用の限界
単一のデモや数回の試行から一般的な生産性向上を断定しない。担当者が規則を守り更新する運用も、導入の前提に含む。
PRACTICE

実践例 — 顧客一覧に担当者フィルターを追加する

架空の応用例

実践例は、既存の顧客管理画面に担当者フィルターを追加する架空の依頼である。ここに示すファイル配置、規則 ID、検査項目、分担は本資料の応用提案。実際のリポジトリ・業務仕様・許可範囲を確認して適用する。

  1. 01

    対象と判断者を定める

    対象は既存の顧客一覧。担当者フィルターを追加する。編集できる範囲と、表示範囲の仕様を決める担当者を確認する。権限に応じたデータ取得をブラウザ内の絞り込みで代替してよいかは推測しない（K01）。

  2. 02

    設計情報を選ぶ

    実在する部品・トークン・画面仕様を探す。DH-C01、DH-X01、DH-S01 は提案用 ID として既存の管理方式に対応付ける。未選択、選択中、空結果、読込中、通信失敗、成功の表示と操作を定める（K02・K03）。

  3. 03

    小さな変更を生成する

    AI に目的、対象画面、許可範囲、必要な参照、状態、受入条件を渡す。既存の部品とデータ取得方式を使い、関連しない一覧機能や API 契約まで変更しない。参照できない契約があれば不足を報告する。

  4. 04

    検査して、人が残りを判断する

    既存の検査を実行し、フィルターの操作と代表状態を描画する。明確な違反は修正・再検査する。失敗時の回復や表示範囲の理解を人が確認する。実行不能は未検証として残す（K04）。

  5. 05

    理由と次の判断条件を残す

    空結果と通信失敗の案内を混同した場合、状態定義と検査を更新する。変更理由、規則 ID、検査結果、人が判断した事項、未検証部分を報告し、同条件の次の変更で再発と運用負担を観測する（K05・K06）。

HANDOFF

AI へ渡す作業指示

この資料の本文と作業指示を一緒に渡す。対象プロジェクトと実装の許可範囲は、依頼者が指定する。

必要な入力

  • 対象リポジトリと画面、利用者、目的、変更を許可する範囲。
  • 承認済み部品・トークン・設計の入口、業務仕様、状態と権限、各情報の管理者。
  • 既存の検査コマンドと実行環境、最終判断者、再現できる問題の証拠。

受入条件

  • 依頼で必要な設計参照が全て解決でき、実装が承認済みの契約に従う。
  • 代表状態と操作について期待値・観測値・証拠を残す。未検証を合格にしない。
  • 明確な違反は修正後に再検査し、人のレビュー項目には判断者と結果を記録する。
  • 既存の権限・データ取得・アクセシビリティ・対応端末の要件を維持する。
  • 規則を更新する場合は適用範囲、理由、例外、検査またはレビュー観点も揃える。

停止・相談条件

  • 権限、データの取得範囲、状態遷移、設計契約が不明で振る舞いを決められない。
  • 業務仕様や API 契約の変更が必要だが、担当者の判断・変更許可が得られていない。
  • 同じ違反の修正が進まず、新しい証拠もない。検査基準を弱めて通過させず、原因と試行結果を報告する。
AI に渡す作業指示の全文
目的: 既存の顧客一覧に担当者フィルターを追加し、合意した設計条件と業務条件に適合させる。
根拠: 添付資料の K01〜K06。規則 ID・ファイル配置・手順は応用提案である。
必要な入力:
- 対象リポジトリと画面、利用者、目的、変更を許可する範囲。
- 承認済み部品・トークン・設計の入口、業務仕様、状態と権限、各情報の管理者。
- 既存の検査コマンドと実行環境、最終判断者、再現できる問題の証拠。

作業:
1. リポジトリの指示、設計の入口、対象画面、データ取得、部品、既存テストを調べる。
2. 実在する参照と提案用 ID を対応付け、目的・対象者・状態・権限・判断者を整理する。
3. 既存契約から少数の適用規則を選び、機械検査と人のレビューに分ける。
4. 許可範囲内で実装する。空結果と通信失敗を区別し、既存の回復・入力保持を維持する。
5. 実在するコマンドで検査し、規則 ID、画面状態、期待値、観測値、証拠を記録する。
6. 明確な違反を修正・再検査し、残るレビューを担当者へ渡す。
7. 再利用すべき判断を、適用範囲と理由付きで設計資料と検査へ戻す。

受入条件:
- 依頼で必要な設計参照が全て解決でき、実装が承認済みの契約に従う。
- 代表状態と操作について期待値・観測値・証拠を残す。未検証を合格にしない。
- 明確な違反は修正後に再検査し、人のレビュー項目には判断者と結果を記録する。
- 既存の権限・データ取得・アクセシビリティ・対応端末の要件を維持する。
- 規則を更新する場合は適用範囲、理由、例外、検査またはレビュー観点も揃える。

停止・相談条件:
- 権限、データの取得範囲、状態遷移、設計契約が不明で振る舞いを決められない。
- 業務仕様や API 契約の変更が必要だが、担当者の判断・変更許可が得られていない。
- 同じ違反の修正が進まず、新しい証拠もない。検査基準を弱めて通過させず、原因と試行結果を報告する。

対象外: 無断の API・権限・業務規則変更、デザインシステム全面刷新、公開・デプロイ。
報告: 変更箇所、使った参照と規則 ID、検査結果、人が判断した事項、未検証、残る判断。
効果: レビュー待ちや再指摘への効果は、実際に測定した結果だけを報告する。
