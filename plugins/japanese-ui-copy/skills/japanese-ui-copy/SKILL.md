# 日本語UIの作成・見直し

利用者が、その場で状態と次の操作を理解できる日本語にする。既存製品の用語集・文体・対象読者を優先する。指定がなければ、一般利用者向けの簡潔で中立的な文体を仮置きし、その仮定を短く伝える。

依頼が作成・レビュー・直接編集のどれかを確認し、その範囲で進める。レビューだけの依頼ではファイルを変更せず、修正候補と理由を返す。調査・確認は対象の画面・操作と、変更が波及する共有文言に絞る。

## 文言を決める

- 操作の対象、実際に起きる結果、現在の状態、適用条件を仕様・実装・周辺の表示から確認する。根拠が足りない場合は不明点を残し、操作の意味や機能を創作しない。調べても解決せず、意味が変わる選択だけ人に確認する。未確定事項は作業報告に分け、利用者向け文言に混ぜない。
- 同じ概念・操作には同じ語を使う。似た語でも動作が違う場合は区別する。用語が未定なら、その案件で採用する語を少数に絞り、作成・見直しの間で共有する。
- ボタンは対象と操作結果が分かる短い表現にする。文脈で明らかな対象は省いてよい。確認画面への移動、保存、送信、削除を区別し、実行前の操作を完了したように書かない。短さのために必要な条件や区別を失わない。
- 見出しは何を扱う場所か、状態表示は現在の状態や何が起きたかを書く。説明は設定の効果、必要な条件、次の操作など、その箇所で必要な情報を伝える。抽象的な宣伝文句、根拠のない効能、不要な敬語、意味のない前置きを足さない。すでに適切な文言は変更しない。
- エラーは判明している事象と、根拠のある対処を書く。原因・データの保存状況・復旧見込み・再試行の安全性を推測で補わない。対処が不明なら無理に案内を作らず、作業報告に要確認事項として残す。
- 意味、主語・対象、否定、条件と例外、数値、単位、期間、概数、可能性、断定の強さを保持する。特に「未満／以下」「前／まで」「可能性がある／必ず」を読み替えない。仕様と文言に矛盾があれば、黙って片方へ合わせず報告する。

## 表示と支援技術向けの文言を揃える

- 表示文言と、支援技術に渡る名前・説明の両方を調べる。HTMLのテキスト、ラベル、代替テキスト、`aria-label`、`aria-labelledby`・`aria-describedby` の参照先、アプリのローカライズ文字列・アクセシビリティ用文言などが対象になる。属性の有無だけでなく、どの文言から実際の名前・説明が得られるかを確認する。すべての文字列リテラルがUI文言とは限らない。
- 表示ラベルとアクセシブルな名前の操作・対象を一致させる。文字の表示ラベルがある操作では、原則としてその文字を名前にも含める。記号のみの操作には機能を表す名前を用意する。既存のラベルから名前が得られる要素へ `aria-label` を一律に追加しない。補足説明と名前を区別し、名前に長い説明を詰め込まない。
- 新規UIでもこの基準を使う。既存UIで名前の欠落や関連付けの不備があり、文言だけで直せない場合は、下記の変更範囲に従って実装の修正事項として扱う。

名前と表示ラベルの関係は [W3C「Label in Name」](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)、名前・説明とその取得元は [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/) を参照できる。Webの仕組みをネイティブアプリへそのまま当てはめず、対象プラットフォームのAPIと実際の取得結果で確かめる。

## 既存の文言を直す

- 文言の内容だけを変更する。識別子、翻訳キー、属性の関連付け、構造、CSS、イベント、処理、値として使う文字列、URL、書式指定子・補間変数の名前・個数・型、複数形の分岐構造は維持する。文言と処理値を兼ねる文字列や、日本語そのものが翻訳キーの文字列も、単なる表示テキストとして置換しない。
- 共有文字列を直す前に参照先を調べ、各画面・状態で同じ表現が成立するか確認する。一括置換で別の操作や対象外の画面まで変えない。
- 画面を直すために文言以外の変更が必要なら、文言の修正とは分けて提案する。既存の明示的な実装依頼があれば、その許可範囲で扱う。
- 差分を確認し、対象外変更が混ざっていないことを確かめる。静的HTMLの範囲検査が使える案件では補助に使うが、それだけで文意や動作の正しさを認定しない。

## 完了前に確かめる

文意・条件の保持、操作とラベルの対応、用語の揺れ、誤字、表示と支援技術向け文言を見直す。生成時も同じ基準を使い、既知の仕様と照合する。ローカライズ資源を編集した場合は、その形式に合う構文・補間の検証も行う。

実際の画面で、代表的な幅・文字拡大・長い値・エラー状態を確認し、不自然な改行、欠落、重なり、はみ出しを調べる。対象と環境に合う範囲で行い、文言だけでは解消できない崩れを隠さない。アクセシブルな名前・説明の取得結果の確認と、実際の読み上げ機器での確認を区別する。

変更点または修正候補とその理由、確認した範囲・結果・未確認事項を短く返す。指摘には対象ファイルや画面を添える。実画面や読み上げ環境を利用できなければ、その確認を未実施と明記し、確認済みと書かない。
