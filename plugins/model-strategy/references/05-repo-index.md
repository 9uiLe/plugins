# リポジトリ索引コンベンション

> **典拠**: `04-large-codebase.md` §6 (恒久資産: リポジトリ索引) を、テンプレートと生成・維持手順まで仕組み化したもの。量制御の原則は `04` に従う。

大規模コードベースで最も効く一度きりの投資。エージェントが「読む」前に「引ける」状態を作り、盲目的な grep + 全読みのトークンを構造的に下げる。`04` §3 の「『読む』を『引く』に変える」を実装する具体物。

## §1 何のための索引か

- **探索を委譲しても、委譲先のサブエージェントが索引を引けば探索コスト自体が下がる** (firewall とインデックスは併用する)
- 索引引き → 該当ファイルだけ範囲読み、を既定動線にする
- 索引はメインにもサブにも安価に常駐する小さなテキスト (全コードの代替にはせず、所在の地図に徹する)

## §2 置き場所 — 索引自身の常駐コストを抑える

> **重要**: 索引は唯一「無料ではない」コンテキスト施策。`CLAUDE.md` の読み込み挙動を踏まえて配置しないと、探索を減らすために**毎ターンの常駐コスト**を払う本末転倒になる (`04` §1 の二次曲線に自分で燃料を足すことになる)。

| 置き場所 | 読み込み | 常駐コスト | 用途 |
| --- | --- | --- | --- |
| ルート + 親ディレクトリの `CLAUDE.md` | 起動時に**先読み (eager)**。`/compact` 後も再注入されて残る | **毎ターン課金**され続ける | リポ全体の薄い地図のみ |
| サブディレクトリの `CLAUDE.md` | そのサブツリーのファイルを読んだ時だけ**遅延 (lazy)** | 触った範囲だけ | 領域ごとの詳細索引 |

### 規定

- **ルート `CLAUDE.md` は薄い「地図の地図」に徹する** — トップ階層のディレクトリ地図と「詳細はどこにあるか」のポインタだけ。公式ガイドの目安 **1 ファイル 200 行以下**を守る
- **詳細な領域別索引はサブディレクトリの `CLAUDE.md` へ** — そのサブツリーを触った時だけ遅延ロードされるので、**常駐コストが「触った範囲」に比例**し、リポ全体サイズに比例しない (= `04` §2「コストを実作業量に比例させる」そのもの)
- パス単位でルールを効かせたいなら `.claude/rules/`(paths frontmatter) も遅延ロードで使える

これにより、巨大リポでも常駐する索引トークンはほぼ一定に保てる。

### 損益分岐

索引が常駐コストの元を取るのは **`索引トークン × ターン数 < 節約できた探索トークン`** のとき。薄いルート + 遅延 nested ならこの不等式は大規模リポほど成立しやすい。逆に**ルートに全索引を盛る**と、左辺がリポ規模に比例して膨らみ、すぐ赤字になる。

## §3 テンプレート

`CLAUDE.md` に以下のセクションを設ける。**所在の地図に徹し、実装詳細は書かない** (詳細はコードが正。索引が古くなると害になる)。

```markdown
## ディレクトリ地図
<!-- 主要ディレクトリと責務を 1 行ずつ。深さは 2〜3 階層まで -->
- `src/api/` — 外部公開 API ハンドラ
- `src/core/` — ドメインロジック (副作用なし)
- `src/adapters/` — DB・外部サービス連携
- `src/jobs/` — 非同期バッチ・スケジュール処理

## エントリポイント
<!-- 実行・ビルド・テストの起点ファイル -->
- アプリ起動: `src/main.ts`
- HTTP ルーティング定義: `src/api/router.ts`
- テスト設定: `vitest.config.ts`

## 機能 → ファイル索引
<!-- 「この機能はどこ」を引けるようにする。横断機能ほど価値が高い -->
- 認証/セッション: `src/api/auth/*`, `src/core/session.ts`
- 課金: `src/core/billing/*`, `src/adapters/stripe.ts`
- 通知: `src/jobs/notify.ts`, `src/adapters/email.ts`

## 横断規約
<!-- 盲目的探索を不要にする規約。命名・レイヤ境界・依存方向 -->
- レイヤ依存方向: `api → core → adapters` (逆流禁止)
- テストは対象ファイルと同階層の `*.test.ts`
- 環境変数は `src/config.ts` に集約 (直接 process.env を読まない)
```

このテンプレは**ルートでは粗く**(トップ階層のみ)、詳細な「機能 → ファイル索引」が増える領域は同名セクションをその領域の**サブディレクトリ `CLAUDE.md`** に置く。ルートは「詳細は各サブツリーの `CLAUDE.md`」と一言ポインタを書けばよい (§2)。

## §4 生成手順 (安価に作る)

索引づくり自体は判断ではなく**作業量タスク**なので、メインでやらず委譲する (`02` 委譲判定・`04` §3)。

1. メインで対象スコープと粒度だけ決める (リポ全体か、特定ツリーか)
2. **`haiku-scout` / `Explore` に委譲**し、戻り値は §3 各セクションを埋めた `CLAUDE.md` ドラフト (= 結論) のみ要求する。生ツリーや全文はメインに持ち帰らせない
3. メインはドラフトを**監査**する: 責務の 1 行説明が正しいか、機能索引に漏れがないか、実装詳細を書きすぎていないか。判断の質が要る部分だけメインが担う
4. 確定したら `CLAUDE.md` にコミットする

> 委譲プロンプト例:
> 「このリポジトリの所在の地図を作る。出力は `CLAUDE.md` のドラフトのみ。セクションは『ディレクトリ地図 / エントリポイント / 機能→ファイル索引 / 横断規約』。各ディレクトリは責務を 1 行で。実装詳細は書かず所在に徹する。生ツリーやファイル全文は返さず、ドラフトだけ返す。」

## §5 維持

- **古い索引は無索引より有害** (誤った所在に誘導し、無駄読みを生む)。所在が変わる変更 (ディレクトリ移動・機能追加) をしたら同じ PR で `CLAUDE.md` を更新する
- 索引が肥大化したら所在の地図に戻す。実装詳細・履歴・TODO は別ファイルへ
- 「索引を引いても該当が見つからない」探索が増えたら、その機能を §3「機能 → ファイル索引」に追記する (索引の自己改善)

## §6 アンチパターン

| アンチパターン | 何が起きるか |
| --- | --- |
| ルート `CLAUDE.md` に全索引を盛る | eager 先読みで**毎ターン常駐課金**。`/compact` でも消えず、二次曲線を自分で加速する |
| 索引に実装詳細・コード断片を書く | すぐ陳腐化し、誤誘導 + 常駐トークン増 |
| `@import` でルート索引を「分割」して軽くしたつもり | import は eager 展開でインラインと同じ。**常駐削減はゼロ**。軽くするには nested CLAUDE.md (遅延) に移すしかない |
| 索引生成をメイン (高単価) でやる | 作業量タスクを最高単価で課金。委譲すべき |
| 所在変更時に索引を更新しない | エージェントが古い地図で無駄読み |
| 全ディレクトリを網羅的に列挙 | 地図が肥大化し常駐コスト増。主要スコープに絞る |
