# Test の責務と境界

Test の追加・削除・統合、または Test Layer の割り当てに迷う時に読む。

## 最初の問い

> この仕様を保証する最も小さい適切な Test Layer はどこか。

小さい Layer で保証できる仕様を、大きい Layer で再検証しない。大きい Layer は、小さい Layer では保証できないことだけを担う。

## Layer ごとの責務

| Layer | 主に保証するもの | 保証しないもの |
| --- | --- | --- |
| Unit | ドメインルール、状態遷移、計算、バリデーション、境界条件、エラー条件 | 外部システムとの実際のやり取り |
| Integration | コンポーネント間の契約、Repository と DataSource、Serialization、Database、API integration | ドメインロジックの全分岐 |
| UI / E2E | 実際のユーザーフロー、画面間遷移、UI からしか保証できない統合、重要な end-to-end scenario | ドメインロジックの全分岐、入力値の全組み合わせ |

例: 割引率の計算規則は Unit Test が全境界を保証する。Integration Test は、計算結果が API の response に正しく serialize されることを 1 ケースで確認する。UI Test は、割引が適用された金額が購入画面に表示される主要フローを確認する。UI Test で割引規則の全分岐を再検証しない。

## Contract Test

コンポーネント間や外部 API との境界で、双方が依存する形（request / response の形、エラーの表現、順序の保証など）を固定する Test。Integration Layer に置き、片側の実装変更で契約が崩れたことを検出させる。契約そのものが仕様なので、呼び出し回数や引数の形を検証してよい。

## Implementation-detail Test を見分ける

次に当てはまる Test は、仕様ではなく How を固定している可能性が高い。

- private な関数・プロパティに直接アクセスしている
- 内部の協調オブジェクトの呼び出し順や回数を検証しているが、それが契約ではない
- 振る舞いを変えないリファクタリングで壊れる
- Test 名が「〜メソッドを呼ぶ」のように手順を表している

**変換の方向:** 内部呼び出しの検証を、観測可能な結果（戻り値、公開された状態、外部への出力）の検証に置き換える。Test 名は「〜の場合、〜になる」という仕様の形にする。

## 削除・統合の基準

次の場合は削除・統合を検討する。

- 同じ仕様を同じ粒度で複数の Test が保証している
- UI Test と Unit Test が同じドメイン分岐を重複して検証している
- private な実装詳細を固定している
- production code の構造変更だけで大量に壊れる
- Test 名は違うが、保証している contract が同じ
- 仕様上意味のない組み合わせを網羅している

上位 Layer から重複した分岐を除くときは、実際の協調先を通る代表的なシナリオを残す。協調先を mock に置き換えて呼び出しを検証する形にすると、その Layer だけが保証できる統合が失われる。

削除する前に、その仕様の保証責任をどの Test が持つかを特定する。保証する Test が残らない場合は、削除ではなく適切な Layer への移動または仕様 Test への変換にする。Test の数を減らすこと自体を目的にしない。

## 不足の判断

Test を追加するのは、仕様のうち保証している Test がないものがある場合だけである。coverage の数値を上げるためだけに Test を追加しない。状態遷移と境界条件は不足が起きやすいので、[state-modeling.md](state-modeling.md) で洗い出した状態・遷移ごとに保証する Test があるかを確認する。
