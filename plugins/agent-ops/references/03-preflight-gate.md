# 着手前ゲート (調査・作戦フェーズ)

指示書の穴は、作業中のエスカレーションや事後の監査ではなく、着手前に露呈させる。監査チェックリストの「独自設計判断の探索」は指示書の穴の事後検出であり、このゲートはその前倒しである。

## 原理: 尋問役はコンテキスト分離する

指示書の曖昧さは、書いた本人と、作成を手伝ったセッションには見えない。同じ文脈で補完して読むためである。ゲートは必ず**指示書作成に関与していないフレッシュセッション**で実行する。実行担当の新規セッションは初見の読者なので、この条件を自然に満たす。指示書作成と同じセッションに尋問させた結果は無効とする。

## 標準ゲート (全委譲で必須)

指示書のマイルストーン M0 として組み込む。定型:

```
M0: まず実装しないでください。
この指示書を満たすために、既存コード・仕様・リスクを調査し、次を短く提示してください。
1. 実装方針
2. 変更対象ファイル
3. 検証方法
4. 未確定事項 — 「確認が必要」と「合理的に仮定して進められる」に分けること。
   各項目に、答えによって実装がどう変わるかを 1 行で添えること。
提示したら停止し、承認を待ってください。
```

- 「確認が必要」には監督役が回答し、指示書の「未確定事項と仮定」セクションへ反映してから M1 を承認する。
- 「仮定して進められる」は仮定の妥当性を確認し、指示書に転記する。
- 「答えによって実装がどう変わるか」を書けない質問は、形骸化した質問として棄却してよい。
- 出た質問の件数と内容は台帳 (04-retrospective-ledger.md) に記録する。質問数の減少傾向が指示書品質の学習曲線である。

## 強化ゲート (高リスク・新規タスク類型)

委譲前に**アンサンブル批評**を追加する。

1. 異なる 2 モデル (例: Opus 4.8 と Codex) のフレッシュセッションに、同じ指示書を独立にレビューさせる: 「作業はするな。未決定の設計判断・複数解釈できる記述・欠けた受け入れ条件・実行側の予想失敗モードを列挙せよ」。
2. 指摘の**和集合**を修正対象、**交差**を最優先とする。独立に収束した指摘は採用確度が高く、片方だけの指摘は盲点の補完として扱う。
3. 「確認が必要」がゼロになるまで指示書更新と批評を反復してから委譲する。

批評役に Fable を使える間の運用は 05-fable-independence.md に従う。
