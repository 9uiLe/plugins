# 知見の資産化ルーティング

知見を 1 文にしてから、落とし先と発火の仕組みを決める。

| 知見の種類 | 落とし先 | 発火 |
| --- | --- | --- |
| スタイル・表記の矯正 (「〜は禁止」) | lint スクリプト + 規約文書に 1 行 | CI・pre-commit・レビュー時に自動 FAIL |
| 反復する手作業 | 自動化スクリプト | コマンド 1 発で再現 |
| 判断を伴う再利用可能な手順 | Skill (`SKILL.md`) | トリガー語で呼び出し |
| 設計判断とその理由 | ADR | 実装時の正典として参照 |
| 環境固有の落とし穴・point-in-time の事実 | memory / プロジェクト docs | 次回セッションの想起 |
| 閾値・予算・ゲート | ゲート設定 + **定期的な形骸化監査** | 超過時 FAIL。ただしゲート自体も疑う |

## 注意

lint に落とせる矯正を `CLAUDE.md` に書くだけで済ませない。書くだけでは発火しない。

## 解説

- スタイル・表記の矯正は、人が覚える規約ではなく機械で落とす。規約文書は理由を残す場所であり、発火は lint に担わせる。
- 反復する手作業は、次回の人間操作を減らす対象である。手順書だけでなく、コマンド 1 発に寄せる。
- 判断を伴う再利用可能な手順は、Skill にしてトリガー語で呼び出せるようにする。1 回きりの判断は Skill にしない。
- 設計判断は ADR に残す。後続実装が「なぜそうしたか」を正典として参照できる必要がある。
- 環境固有の落とし穴や point-in-time の事実は、memory やプロジェクト docs に置く。普遍的な手順として一般化しない。
- 閾値・予算・ゲートは、超過時に FAIL する仕組みにする。ただしゲート自体が形骸化していないか、定期的に疑う。
