# 指示書テンプレート

外部エージェントへ作業を渡す前に、このテンプレートをコピーして正典として固定する。

```markdown
# 指示書: <作業名>

## 0. 役割と絶対制約

あなたは <対象リポジトリ/対象範囲> の実装担当です。レビューは <監督役> が行います。

- この指示書が正典です。指示書にない設計判断はしないでください。
- 迷った場合は停止して質問するか、最終報告の「未解決の質問」に列挙してください。
- git 操作、不可逆操作、外部送信、公開設定変更の可否をここに明記してください。
- スコープ外ファイル・ディレクトリには触れないでください。

## 1. 背景と正典リンク

- 目的:
- 参照すべき ADR:
- 参照すべき仕様:
- 参照すべき既存コード:

## 2. 作業スコープ

- 追加・変更する成果物:
- 触ってよい既存ファイル:
- 触ってはいけない既存ファイル:

## 3. 非目標

- やらないこと (リファクタ、後方互換対応、周辺改善など):

## 4. 未確定事項と仮定

- 確認が必要 (回答があるまで該当作業に着手しない):
- 仮定して進めてよい (採用した仮定は最終報告に列挙):

## 5. 事前調査

- 実装前に読むべきコード・仕様・過去の類似変更:

## 6. マイルストーンと停止点

- M0 (必須): 調査・作戦フェーズ。実装せず、実装方針・変更対象・検証方法・未確定事項 (「確認が必要」と「仮定して進められる」に二分) を提示して停止。
- M1:
- 各マイルストーン完了で停止し、承認を待つ。次に着手しない。

## 7. 受け入れ条件

- `command-that-verifies-build`
- `command-that-verifies-tests`
- `command-that-verifies-lint`

## 8. 完了報告フォーマット

1. 変更ファイル一覧
2. 検証コマンドと生ログ
3. 指示書から外れた点・裁量で決めた点
4. 採用した仮定と未解決の質問
```

## 書き方

- **役割と絶対制約**: 「この指示書が正典。指示書にない設計判断はしない。迷ったら停止して質問 (または報告に列挙)」を必ず含める。実装エージェントの独自設計判断は、テストをすり抜けるバグの最大発生源だった。
- **禁止事項の明文化**: git 操作の可否、不可逆操作 (公開設定変更・削除・外部送信) を誰が行うか、スコープ外ファイル・ディレクトリを列挙する。ビルド生成物を成果物に含めるかも明記する。
- **背景と正典リンク**: 目的、参照すべき ADR・仕様・既存コードを書く。リンクのない口頭仕様だけにしない。
- **作業スコープ**: 対象ファイル・成果物を列挙する。既存ファイルの変更を許可する場合はファイル名まで狭める。
- **非目標**: 成果物レベルでやらないことを書く。「触ってはいけないファイル」だけでは足りない。リファクタ・後方互換・周辺改善など、実行側が善意で広げがちな範囲を明示的に閉じる。
- **未確定事項と仮定**: 着手前ゲート (03-preflight-gate.md) の M0 出力に監督役が回答し、ここに反映する。「確認が必要」が残ったまま M1 を承認しない。
- **事前調査**: 暗黙コンテキストの掘り出しを明示的な作業項目にする。実行側は頼まれない限り文脈を探索しない前提で書く。
- **マイルストーンと停止点**: M0 (調査・作戦フェーズ) を必ず先頭に置く。「M1 完了で停止、承認を待つ。次に着手しない」形式にする。失敗コストが大きい・著者の判断に自信がない場合はマイルストーン粒度を上げ、先見性を検証で代替する。
- **受け入れ条件**: 機械的に検証可能なコマンドで書く。ビルド・テスト・lint を曖昧な自己申告にしない。
- **報告フォーマット**: 変更ファイル一覧、検証コマンドと生ログの貼り付け、採用した仮定と未解決の質問を必須にする。
