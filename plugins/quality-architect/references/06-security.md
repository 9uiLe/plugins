# 06. セキュリティ / Security

> ISO/IEC 25010:2023 製品品質モデルの「セキュリティ」に関する、調査・アーキテクチャ設計・コードレビュー用リファレンス。
> 本ドキュメントは **ISO/IEC 25010:2023** に準拠し、6 つの副特性（機密性・インテグリティ・否認防止性・責任追跡性・真正性・耐性）を扱う。
>
> **2011 版との差異**: ISO/IEC 25010:2011 では副特性は 5 つ（機密性・インテグリティ・否認防止性・責任追跡性・真正性）であり、**耐性（Resistance）は存在しない**。ISO/IEC 25010:2023 で正式な第 6 副特性として追加された。

---

## 1. 定義

**セキュリティ（Security）** とは、製品またはシステムが情報および機能を保護し、認可された主体にのみアクセスを許可しながら、認可されていない主体による不正アクセス・改ざん・漏えいを防止し、攻撃を受けながらも意図した機能を維持できる度合いである（ISO/IEC 25010:2023 の主旨に基づく要約）。

ISO/IEC 25010:2023 では、セキュリティを以下の **6 副特性** で構成する。

| 副特性 | 英語 | 概要 |
|---|---|---|
| 機密性 | Confidentiality | 認可された主体のみが情報にアクセスできることを保証する度合い |
| インテグリティ（完全性） | Integrity | システムおよびデータが悪意ある操作やエラーによる不正な変更・削除から守られている度合い |
| 否認防止性 | Non-repudiation | 行動またはイベントが発生したことを後から否定できない形で証明できる度合い |
| 責任追跡性 | Accountability | エンティティが実行した行動を、そのエンティティに一意にトレースできる度合い |
| 真正性 | Authenticity | 主体またはリソースのアイデンティティが主張通りであることを証明できる度合い |
| 耐性 | Resistance | 攻撃を受けている状況下でも、製品が本来の機能を維持し続けられる度合い |

> **2011 版との差異**: ISO/IEC 25010:2011 では耐性（Resistance）は副特性に含まれず、セキュリティは 5 副特性で構成されていた。ISO/IEC 25010:2023 で耐性が正式な第 6 副特性として追加された（§2.6 参照）。

CIA トライアド（機密性・完全性・可用性）はセキュリティの古典的基盤だが、ISO/IEC 25010 はこれを否認防止性・責任追跡性・真正性・耐性でさらに拡張している。

## 2. 副特性

### 2.1 機密性（Confidentiality）

#### 定義
情報へのアクセスを認可された主体だけに限定し、権限のない者には開示しない仕組みが整っている度合い。（出典: ISO/IEC 25010:2011 §4.2.6.1 の主旨に基づく要約）

#### 調査観点
- 保護対象データ（PII・秘密鍵・認証情報）の洗い出しと分類が行われているか。
- 転送時（TLS/HTTPS）および保存時（暗号化ストレージ）のデータ保護。
- アクセス制御モデル（RBAC/ABAC）が設計・実装されているか。

#### 設計タクティクス・パターン
- **最小権限原則（Least Privilege）**：Saltzer & Schroeder (1975) が定式化した原則。主体に必要最小限のアクセス権のみを付与する。
- **完全な仲介（Complete Mediation）**：すべてのリソースアクセスを認可チェックの対象とする。
- **転送暗号化**：TLS 1.3 以上を要求し、古いプロトコル（SSL/TLS 1.0/1.1）を無効化する。
- **保存暗号化**：AES-256-GCM 等の認証付き暗号を採用する。
- **秘密情報の分離**：設定ファイル・ソースコードへの認証情報ハードコーディングを禁止し、Secrets Manager を使用する。

#### コードレビューチェックリスト
- [ ] 認証情報・API キーがソースコード・ログに露出していない。
- [ ] ログ出力に個人情報・機密情報が含まれていない。
- [ ] レスポンスにアプリケーションの内部構造情報（スタックトレース等）が含まれていない。
- [ ] 暗号化アルゴリズムが組織基準（NIST SP 800-53 SC-28）を満たしている。
- [ ] 不要なポートやサービスが公開されていない。

#### 計測指標
- 平文で保存された機密データ件数（目標: 0）
- 暗号化なし API エンドポイント数（目標: 0）
- OWASP ASVS V6 暗号要件の充足率（%）

---

### 2.2 インテグリティ（Integrity）

#### 定義
悪意ある操作やコンピュータエラーによって、システムの状態やデータが無断で書き換えられたり削除されたりしない状態を維持できる度合い。（出典: ISO/IEC 25010:2011 §4.2.6.2 の主旨に基づく要約）

#### 調査観点
- 入力バリデーションが適切に実施されているか（インジェクション・改ざん対策）。
- データベース・ファイルシステムへの書き込みが認可されたパスのみか。
- ソフトウェアサプライチェーン（依存ライブラリ・ビルド成果物）の整合性が保証されているか。

#### 設計タクティクス・パターン
- **入力バリデーション**：信頼境界を越えるすべての入力をサーバサイドで検証する。
- **パラメータ化クエリ / ORM**：SQL インジェクション（OWASP Top 10:2025 A05）を排除する。
- **HMAC・デジタル署名**：メッセージ・成果物の完全性を暗号的に保証する。
- **チェックサム検証**：配布バイナリおよびコンテナイメージの整合性をデプロイ前に確認する。
- **書き込み権限の最小化**：ファイルシステム・データベーステーブルへのアクセスを読み取り専用に絞る。

#### コードレビューチェックリスト
- [ ] SQL/NoSQL クエリに文字列連結が使われていない（パラメータ化済み）。
- [ ] ファイルアップロード処理でコンテンツタイプ・拡張子・マジックバイト検証が実施されている。
- [ ] 外部ライブラリのバージョンが固定（lockfile）されており、ハッシュ検証が有効。
- [ ] 重要データの変更操作が監査ログに記録されている。
- [ ] ORM や DB 権限が最小権限に設定されている。

#### 計測指標
- 静的解析（SAST）で検出されたインジェクション脆弱性件数
- 依存ライブラリの既知脆弱性（CVE）件数
- OWASP ASVS V5 入力バリデーション要件の充足率（%）

### 2.3 否認防止性（Non-repudiation）

#### 定義
特定の行動やイベントが確かに起きたという事実を、当事者が後から覆せない形で証明できる度合い。（出典: ISO/IEC 25010:2011 §4.2.6.3 の主旨に基づく要約）

#### 調査観点
- 重要操作（取引・ログイン・データ変更）に対して改ざん不能な証跡が存在するか。
- デジタル署名・タイムスタンプ機構が実装されているか。
- 監査ログが外部から書き換えられない保護下に置かれているか。

#### 設計タクティクス・パターン
- **デジタル署名**：PKI（X.509 証明書）および非対称暗号を用いて送信者の行動を確定する。
- **RFC 3161 タイムスタンプ**：信頼できる第三者による時刻証明でイベント発生時刻を保護する。
- **Write-Once ログストレージ**：S3 Object Lock・WORM ストレージにより監査ログへの上書きを物理的に禁止する。
- **ブロックチェーン / 分散台帳**：高い否認防止が要求されるユースケースでの改ざん不能記録。
- **STRIDE「否認（Repudiation）」脅威対策**：Microsoft SDL のデータフロー分析でログ欠如を検出する。

#### コードレビューチェックリスト
- [ ] 重要ビジネスイベントに操作者・タイムスタンプ・内容を含むログが残っている。
- [ ] 監査ログへの削除・更新 API が存在しない。
- [ ] デジタル署名の検証処理が、鍵の有効期限・失効確認（OCSP/CRL）を含めて実装されている。
- [ ] ログのハッシュチェーンまたは外部への転送が定期実行されている。

#### 計測指標
- 監査ログカバレッジ率（重要操作に占めるログ記録済み操作の割合）
- ログ改ざん検知の誤検知率（FPR）

---

### 2.4 責任追跡性（Accountability）

#### 定義
システム上で行われた操作を、それを実行したエンティティまで確実に追跡・特定できる度合い。（出典: ISO/IEC 25010:2011 §4.2.6.4 の主旨に基づく要約）

#### 調査観点
- 各アクション・リクエストを実行者（ユーザー ID・サービスアカウント）と紐付けられるか。
- 共有アカウント・サービスアカウントが乱用されていないか。
- ログが集中管理され、相関分析が可能か。

#### 設計タクティクス・パターン
- **一意識別子の付与**：すべてのユーザー・サービスアカウントに一意 ID を割り当て、共有アカウントを排除する。
- **リクエストコンテキスト伝搬**：マイクロサービス間で Correlation ID・ユーザーコンテキストを HTTP ヘッダで伝搬する。
- **SIEM 統合**：NIST SP 800-53 Rev.5 AU ファミリ（監査・説明責任）の要件に基づき、集中ログ管理基盤を構築する。
- **最小共有（Least Common Mechanism）原則**：Saltzer & Schroeder のメカニズム共有最小化原則に基づき、ユーザー間で状態を共有しない。
- **セッション管理**：セッションはユーザーに紐付け、並列セッションを制限する（NIST SP 800-63B-4 §5 セッション管理参照）。

#### コードレビューチェックリスト
- [ ] すべての API コールにリクエスト元の識別子（ユーザー ID・IP・セッション ID）がログに含まれている。
- [ ] 管理操作・権限昇格に対して追加の承認フロー・ログが存在する。
- [ ] サービスアカウントが個人ユーザーと共用されていない。
- [ ] ログに個人識別情報を含める場合、プライバシー規制（GDPR 等）への対応が考慮されている。

#### 計測指標
- 識別子なしリクエスト率（目標: 0%）
- 平均ログ保持期間（法令・NIST SP 800-53 AU-11 要件との比較）

### 2.5 真正性（Authenticity）

#### 定義
通信相手やリソースが本当に名乗り通りの存在であると検証・確認できる度合い。（出典: ISO/IEC 25010:2011 §4.2.6.5 の主旨に基づく要約）

#### 調査観点
- 認証メカニズムが保証レベル（AAL）の要件を満たしているか。
- トークン・証明書の偽造・盗用に対する保護があるか。
- マシン間認証（サービスメッシュ・API）にも真正性が確保されているか。

#### 設計タクティクス・パターン
- **多要素認証（MFA）**：NIST SP 800-63B-4 が定義する AAL2/AAL3 レベルの認証を採用する。パスワード単独は AAL1 に留まる。
- **FIDO2/WebAuthn**：フィッシング耐性を持つ公開鍵認証。NIST SP 800-63B-4 で AAL2/AAL3 要件を満たす認証器として承認。
- **相互 TLS（mTLS）**：サービス間通信において双方向証明書認証を実施する。
- **JWT / OAuth 2.0 / OpenID Connect**：署名付きトークンで API クライアントの真正性を確保する。OWASP ASVS 5.0 セッション管理要件を参照。
- **証明書のピンニング（Certificate Pinning）**：モバイル・IoT 環境において中間者攻撃を防止する。
- **Fail-safe Defaults（フェイルセーフデフォルト）**：Saltzer & Schroeder の原則。認証失敗時はデフォルトで拒否する。

#### コードレビューチェックリスト
- [ ] パスワードが bcrypt/Argon2 等の適切なハッシュアルゴリズムで保存されている（平文・MD5 禁止）。
- [ ] JWT の署名アルゴリズムが `alg: none` を許可していない。
- [ ] トークンの有効期限が適切に設定されており、リフレッシュトークンのローテーションが実装されている。
- [ ] 認証失敗時のエラーメッセージがユーザー名・パスワードどちらが誤りかを区別しない。
- [ ] サービスアカウントの認証情報が定期ローテーションされる仕組みがある。
- [ ] OWASP Top 10:2025 A07 認証の失敗（Authentication Failures）に相当する問題がない。

#### 計測指標
- MFA 有効化率（管理者: 目標 100%、一般ユーザー: 組織基準による）
- 認証関連インシデント件数（フィッシング・クレデンシャルスタッフィング等）
- NIST SP 800-63B-4 AAL 達成レベル

### 2.6 耐性（Resistance）

#### 定義
攻撃を受けている状況下でも、製品が本来の機能を維持し続けられる度合い。（出典: ISO/IEC 25010:2023 の主旨に基づく要約）

> **2011 版との差異**: 耐性は ISO/IEC 25010:2011 には存在せず、**ISO/IEC 25010:2023 で追加された第 6 の副特性**である。STRIDE フレームワークの DoS（サービス拒否）脅威に直接対応する副特性として位置づけられる。

#### 調査観点
- DoS/DDoS 攻撃に対するレートリミット・WAF・CDN による防護が存在するか。
- 入力フラッディング・リソース枯渇攻撃（メモリ・CPU・コネクション）への対策があるか。
- 高負荷状態でも基本機能が維持されるグレースフルデグレード設計が施されているか。
- 攻撃シナリオを前提にした負荷テスト・ペネトレーションテストが実施されているか。

#### 設計タクティクス・パターン
- **レートリミット・スロットリング**：API ゲートウェイ・リバースプロキシレベルで過剰リクエストを遮断する。ユーザー単位・IP 単位・エンドポイント単位の多段制限が有効。
- **WAF（Web Application Firewall）**：OWASP CRS（Core Rule Set）を適用し、既知の攻撃パターン（SQLi・XSS・ボット）を遮断する。
- **DDoS 緩和サービス**：CDN（Cloudflare・AWS Shield 等）によるトラフィック吸収・スクラビングセンターへの迂回でボリューム攻撃を緩和する。
- **サーキットブレーカー**：連鎖障害を防止し、部分的な攻撃影響がシステム全体に波及しないよう遮断する。
- **入力サイズ・複雑度の制限**：ペイロードサイズ・ネストの深さ・リクエスト数の上限を設け、バッファ枯渇や正規表現 ReDoS を防ぐ。
- **グレースフルデグレード**：攻撃により一部機能が影響を受けても、コア機能の継続稼働を保証する縮退設計を採用する。

#### コードレビューチェックリスト
- [ ] 外部入力のサイズ・深さ・繰り返し回数に上限が設定されている。
- [ ] 認証試行失敗に対してアカウントロックまたは指数バックオフ遅延が実装されている。
- [ ] API エンドポイントにレートリミット（ユーザー単位・グローバル単位）が設定されている。
- [ ] バックグラウンドジョブ・メッセージキューにスロットリングおよびキュー長上限が設定されている。
- [ ] 正規表現に ReDoS（カタストロフィックバックトラッキング）の危険がない。
- [ ] 攻撃シナリオを想定した負荷テスト・ペネトレーションテストの計画が存在する。

#### 計測指標
- レートリミット発動率（観測期間中に制限に達したリクエストの割合）
- 攻撃時の基本機能維持率（グレースフルデグレード達成率）
- OWASP ASVS V4 DoS/DDoS 関連要件の充足率（%）

## 3. 横断的な設計戦略

### 3.1 脅威モデリング（STRIDE）
Microsoft SDL で体系化された STRIDE フレームワークは、6 種の脅威カテゴリを ISO/IEC 25010 副特性に対応づける。

| STRIDE 脅威 | 説明 | 対応副特性 |
|---|---|---|
| **S**poofing（なりすまし） | 偽の主体として振る舞う | 真正性 |
| **T**ampering（改ざん） | データ・コードの不正変更 | インテグリティ |
| **R**epudiation（否認） | 行動の事後否定 | 否認防止性 |
| **I**nformation Disclosure（情報漏えい） | 機密情報の不正開示 | 機密性 |
| **D**enial of Service（サービス拒否） | 可用性の破壊 | 耐性 |
| **E**levation of Privilege（権限昇格） | 不正な権限取得 | 責任追跡性・真正性 |

### 3.2 Saltzer & Schroeder の 8 設計原則
1975 年に提唱されたこれらの原則は現在も基本指針として有効である（*Proceedings of the IEEE*, Vol.63, No.9, 1975）。

| 原則 | 概要 |
|---|---|
| Economy of Mechanism | 設計をシンプルかつ小規模に保つ |
| Fail-safe Defaults | アクセス決定は拒否をデフォルトとする |
| Complete Mediation | すべてのアクセスを毎回認可チェックする |
| Open Design | セキュリティはメカニズムの秘匿に依存しない |
| Separation of Privilege | 複数条件の充足を要求する |
| Least Privilege | 必要最小限の権限のみを付与する |
| Least Common Mechanism | メカニズム共有を最小化する |
| Psychological Acceptability | セキュリティ機構はユーザーが容易に利用できる |

### 3.3 多層防御（Defence in Depth）
ISO/IEC 27002:2022 の統制分類（組織・人的・物理・技術）に基づき、単一の技術的統制への依存を避ける。ネットワーク境界・アプリケーション層・データ層のそれぞれにセキュリティ統制を配置する。

### 3.4 セキュア SDLC との統合
OWASP ASVS 5.0（2025 年 5 月リリース）の 3 レベル（L1: 基本、L2: 標準、L3: 高保証）を要件定義フェーズで採択し、各フェーズの活動（設計レビュー・SAST・DAST・ペネトレーションテスト）に紐付ける。ASVS 5.0 では要件数が約 350 項目（17 章）に拡張され、ポスト量子暗号への対応や AI・クラウドネイティブ向けの要件が追加されている。

## 4. レビュー時の重点チェックリスト（要約）

以下は設計レビューおよびコードレビューで確認すべき最重要項目の要約である。

### 認証・認可
- [ ] 認証に MFA が実装されている（管理者は必須）
- [ ] アクセス制御が全 API エンドポイントに適用されている（OWASP Top 10:2025 A01 対策）
- [ ] 認証失敗時の応答が均一（タイミング攻撃・情報漏えい対策）

### データ保護
- [ ] 機密データが転送時・保存時ともに暗号化されている
- [ ] 暗号化アルゴリズムが NIST 承認アルゴリズムである（AES-256、RSA-2048 以上、ECDSA P-256 以上）
- [ ] 鍵管理プロセスが定義されており、ハードコーディングが存在しない

### 入力・出力
- [ ] すべての外部入力がサーバサイドで検証されている
- [ ] 出力エンコーディングが実施されている（XSS 対策）
- [ ] SQL/NoSQL/LDAP クエリがパラメータ化またはエスケープされている

### 監査・証跡
- [ ] 重要操作の監査ログが操作者・日時・対象を含む
- [ ] ログが改ざん防止された場所に保存されている
- [ ] セキュリティイベントのアラートが設定されている

### 依存コンポーネント
- [ ] 使用ライブラリの既知 CVE が定期スキャンされている
- [ ] コンテナ・OS イメージが最新セキュリティパッチを適用している

### 耐性
- [ ] 外部入力のサイズ・ネスト深度・繰り返し回数に上限が設定されている
- [ ] API エンドポイントにレートリミットが設定されている
- [ ] 認証失敗に対してアカウントロックまたはバックオフが実装されている
- [ ] 攻撃時でもコア機能が縮退稼働できるグレースフルデグレード設計が存在する

## 5. アンチパターン

| アンチパターン | リスク | 対策 |
|---|---|---|
| **セキュリティ・バイ・オブスキュリティ** | 難読化のみに依存し、根本的な保護がない | Open Design 原則を適用し、暗号的手法で保護 |
| **神クラスの権限管理** | 単一モジュールで全認可を管理し変更困難 | RBAC/ABAC を専用サービス・ミドルウェアへ分離 |
| **ログへの機密情報出力** | パスワード・トークンがログに平文記録 | ログマスキング・サニタイゼーションを実装 |
| **共有サービスアカウント** | インシデント発生時に個人追跡が不可能 | サービスごとに専用 ID を発行し責任追跡性を確保 |
| **暗号化なし内部通信** | 内部ネットワーク侵害で全トラフィックを盗聴される | Zero Trust アーキテクチャ（mTLS）を適用 |
| **クライアントサイド認可のみ** | UI の改ざんで権限チェックをバイパス可能 | 認可ロジックは必ずサーバサイドで実施 |
| **ハードコードされた認証情報** | ソースコードリポジトリ経由で認証情報が漏えい | Secrets Manager / 環境変数に外部化 |
| **無制限のエラー詳細レスポンス** | スタックトレース・DB スキーマが攻撃者に開示 | 本番環境でエラー詳細を非表示にする |
| **セッションの無失効** | 盗まれたトークンが永続的に有効 | 適切な有効期限・ログアウト時の無効化を実装 |
