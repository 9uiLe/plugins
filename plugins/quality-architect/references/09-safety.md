# 09. 安全性 / Safety

> **ISO/IEC 25010:2023 で新設された特性**。ISO/IEC 25010:2011 には存在しない。2023 年改訂で 9 番目の製品品質特性として追加され、人・財産・環境への許容できないリスクを明示された条件下で回避・制御・維持する度合いを定める。
>
> 本ドキュメントは **ISO/IEC 25010:2023** に準拠し、5 つの副特性（運用上の制約・リスク識別・フェイルセーフ・ハザード警告・安全な統合）を扱う。

---

## 1. 定義

**安全性 (Safety)** とは、ISO/IEC 25010:2023 が定める第 9 の品質特性であり、システムまたは製品が、明示された条件のもとで運用されるとき、人の生命・健康、財産、または環境に対して許容できないレベルのリスクをもたらさない度合いを示す。（出典: ISO/IEC 25010:2023 §4.2.9 の主旨に基づく要約）

安全性の核心は「危険 (hazard) が存在する状況でも、リスクを許容可能な範囲に抑制し続けること」にある。これは IEC 61508 が定義する**機能安全 (Functional Safety)**—「E/E/PE システムが、要求された安全機能を正確に実行することで、リスクを許容可能なレベルまで低減する」概念—とも整合する。

Leveson（2012）の STAMP (Systems-Theoretic Accident Model and Processes) は、事故を個別コンポーネントの故障ではなくシステム全体の制御構造の破綻として捉え、設計段階からの安全性作り込みを重視する現代的枠組みを提供する。

| 副特性 | 英語 | 概要 |
|--------|------|------|
| 運用上の制約 | Operational constraint | ハザード遭遇時に安全なパラメータ・状態内に動作を制限する度合い |
| リスク識別 | Risk identification | 許容できないリスクにつながり得る事象・操作の連鎖を識別する度合い |
| フェイルセーフ | Fail safe | 故障時に自動的に安全な動作モードへ移行・復帰できる度合い |
| ハザード警告 | Hazard warning | 許容できないリスクに対し十分な警告と余裕時間を提供する度合い |
| 安全な統合 | Safe integration | 他コンポーネントと統合する間も統合後も安全性を維持できる度合い |

## 2. 副特性

### 2.1 運用上の制約 (Operational Constraint)

#### 定義
ハザードが発生している、またはハザードが予見される状況において、製品またはシステムが自身の動作を安全なパラメータ・状態の範囲内に制限できる度合い。スロットリング・動作モード切替・機能縮退など、運用中のリアルタイム制約実施能力が問われる。（出典: ISO/IEC 25010:2023 主旨に基づく要約）

#### 調査観点
- 危険状態の検知条件と、その際にシステムが自動的に制限を課す仕組みの有無
- 許容される動作パラメータ（速度・温度・圧力・処理レート等）の上下限の明示的定義
- 制限解除の条件・権限・手順が明確化されているか
- 制約実施の応答時間要件（リアルタイム性）
- IEC 61508 の SIL（Safety Integrity Level）や ISO 26262 の ASIL に相当する安全要求レベルの割り当て

#### 設計タクティクス・パターン
- **動作エンベロープ強制 (Operational Envelope Enforcement)**: センサー値や計算結果が安全限界を超えた場合に自動的に動作を制限する。IEC 61508 Part 3 はこの制御ロジックに SIL 対応の開発手法を要求する。
- **機能縮退モード (Degraded Mode Operation)**: 完全機能が維持できない状況で、より安全な制限された機能セットに自動移行する。ISO 26262 では ASIL 分解（ASIL decomposition）により冗長化と組み合わせて実現する。
- **レートリミッタ・ガードレール**: 処理レート・出力値・制御入力に上限を設け、コード・ハードウェア双方で二重に実施する。
- **安全モニタリングループ**: 主制御ループとは独立した監視ループが動作パラメータを継続的に検証し、違反を検知する（独立性は IEC 61508 の要件）。

#### コードレビューチェックリスト
- [ ] 安全限界値（上限・下限）がハードコードまたは設定ファイルで明示されており、変更には認可が必要か
- [ ] 制限条件のトリガーロジックが独立したモジュール・プロセスとして実装されているか
- [ ] 機能縮退モードへの移行が自動かつ確実に行われ、移行失敗時の対処が定義されているか
- [ ] 制約実施のレイテンシがリアルタイム要件を満たしているか（タイミング解析が実施されているか）
- [ ] 安全限界パラメータの変更履歴が追跡可能か（構成管理）

#### 計測指標
| 指標 | 説明 |
|------|------|
| 制約応答時間 | ハザード検知から動作制限実施までの最大時間（ms） |
| 制約違反率 | 安全限界外で動作した時間 / 総運用時間 × 100 % |
| 縮退モード移行成功率 | 縮退モード移行試行のうち成功した割合（%） |

### 2.2 リスク識別 (Risk Identification)

#### 定義
運用の継続が人の生命・財産・環境に対して許容できないリスクにつながり得る、事象または操作の連鎖をシステムが識別できる度合い。事後的な障害分析だけでなく、動作中のリアルタイムリスク検知能力も含む。（出典: ISO/IEC 25010:2023 主旨に基づく要約）

#### 調査観点
- 設計段階での体系的ハザード分析（HAZOP / FMEA / FTA / STPA）の実施有無
- システムが実行時に異常状態・リスク兆候を検出する機能の有無
- リスクシナリオのカバレッジ（識別されたハザードと対策のトレーサビリティ）
- リスク識別の更新プロセス（変更・インシデント後の再評価）
- ISO 21448 (SOTIF) が対象とする、意図した機能の限界に起因するリスク（機能不足起因）の考慮

#### 設計タクティクス・パターン
- **HAZOP (Hazard and Operability Study)**: ガイドワード（多すぎる・少なすぎる・逆など）を用いてプロセス設計の各ノードを系統的に審査し、ハザードと運用上の問題を識別する。
- **FMEA (Failure Mode and Effects Analysis)**: 各コンポーネントの潜在的故障モードとその影響・重大度を列挙し、優先度付きリスク対策（RPN: Risk Priority Number）を導出する。
- **FTA (Fault Tree Analysis)**: 望まない最上位事象（トップイベント）から下向きに論理ゲートで原因を展開し、定性的・定量的なリスク分析を行う。
- **STPA (System-Theoretic Process Analysis)**: Leveson（2012）が提案する現代的手法。制御構造における不適切な制御行為 (Unsafe Control Action: UCA) を識別し、従来の故障モデルでは捉えられないシステム的原因を分析する。
- **ランタイム監視・アノマリ検知**: センサーフュージョン、統計的プロセス管理（SPC）、または機械学習ベースの異常検知でリアルタイムリスク識別を実現する。

#### コードレビューチェックリスト
- [ ] 設計段階での FMEA / HAZOP / FTA 等のハザード分析が文書化されており、コードに対策が反映されているか
- [ ] 識別されたリスクシナリオに対するテストケースが存在するか（ハザード駆動テスト）
- [ ] 異常状態の検知ロジックが適切な閾値・時間窓で設定されているか
- [ ] 新たなリスクが識別された場合の報告・記録・対策ループが定義されているか
- [ ] 第三者ライブラリ・外部システム起因のリスクが分析対象に含まれているか

#### 計測指標
| 指標 | 説明 |
|------|------|
| ハザードカバレッジ率 | 対策が実装済みのハザード数 / 識別済みハザード総数 × 100 % |
| ランタイムリスク検知率 | テストシナリオで検知できたリスク事象数 / 注入リスク事象総数 × 100 % |
| FMEA RPN 上位件数 | RPN 閾値（例: 200）超の未対処リスク件数（目標: 0） |

### 2.3 フェイルセーフ (Fail Safe)

#### 定義
ソフトウェアやハードウェアに故障が生じたとき、製品が自動的に安全な動作モードに移行するか、安全な状態へ復帰できる度合い。「故障 = 危険な状態」とならないよう設計する原則。（出典: ISO/IEC 25010:2023 主旨に基づく要約）

#### 調査観点
- 故障の種別（ハードウェア故障・ソフトウェアクラッシュ・通信途絶・電源断）ごとの安全状態の定義
- 安全状態への移行が自動かつ確実に起動されるか（人間の介入を要さないか）
- IEC 61508 SIL / DO-178C DAL 要件に対応したフェイルセーフ機構の冗長性
- フェイルセーフ機構自体の故障モード（フェイルセーフが失敗するケース）の分析

#### 設計タクティクス・パターン
- **ウォッチドッグタイマー (Watchdog Timer)**: ソフトウェアが一定間隔で「生存確認信号 (kick)」を送出し、途絶えた場合にハードウェアがシステムリセットまたは安全出力への切り替えを強制する。IEC 61508 および DO-178C DAL A/B では独立ウォッチドッグの使用を推奨する。チャレンジ・レスポンス型ウォッチドッグは最高安全レベル（ASIL-D / SIL 4）で有効。
- **フェイルサイレント / フェイルストップ設計**: 故障を検知したコンポーネントが出力を即時停止し、下流コンポーネントへ誤情報を伝播させない。
- **安全状態遷移 (Safe State Transition)**: 有限状態機械 (FSM) として安全状態を明示的にモデル化し、故障イベントを受信した際の遷移を仕様に組み込む。
- **冗長化 (Redundancy)**: TMR（Triple Modular Redundancy）等の投票アーキテクチャにより、単一故障が安全機能の喪失に直結しない設計とする。
- **故障検知・隔離・回復 (FDIR: Fault Detection, Isolation, and Recovery)**: 航空・宇宙で標準化された三段階プロセス。検知（異常状態の識別）→隔離（故障コンポーネントの切り離し）→回復（代替機能への切り替え）。

#### コードレビューチェックリスト
- [ ] ウォッチドッグタイマーが実装され、キック処理がクリティカルなコードパスから独立して行われているか
- [ ] システムが取り得る「安全状態」が FSM として明示的に定義されているか
- [ ] 例外・クラッシュ・タイムアウトのすべての経路で安全状態への移行が保証されているか
- [ ] フェイルセーフ機構自体が SIL/ASIL 要件を満たす独立コンポーネントで実装されているか
- [ ] 安全状態移行のテスト（故障注入テスト）が実施されているか

#### 計測指標
| 指標 | 説明 |
|------|------|
| 安全状態移行成功率 | 故障注入テストで安全状態に移行した試行数 / 全注入試行数 × 100 % |
| ウォッチドッグ検知時間 | ソフトウェア停止からウォッチドッグトリガーまでの最大時間（ms） |
| PFD（要求時故障確率） | IEC 61508 の SIL 評価指標。安全機能が要求された際に失敗する確率 |

### 2.4 ハザード警告 (Hazard Warning)

#### 定義
許容できないリスクが迫りつつある状況において、オペレータや内部制御機構に対して、安全な運用を継続するために十分な余裕時間をもって警告を発することができる度合い。警告の適時性・明瞭性・信頼性が問われる。（出典: ISO/IEC 25010:2023 主旨に基づく要約）

#### 調査観点
- 警告の発令タイミング（危険状態に至る前に十分な余裕があるか）
- 警告の識別性（緊急度に応じた表現の差別化、誤警告の抑制）
- 警告不達のリスク（通信障害・UI 不可視など）と冗長な警告経路の有無
- ISO 21448 (SOTIF) における「システムの限界を超えたシナリオ」に対する警告の考慮
- 誤警告 (false positive) 率の管理（警告疲れ＝alarm fatigue の防止）

#### 設計タクティクス・パターン
- **アラームの階層化**: 緊急度に応じて情報 (Information)・警告 (Warning)・危険 (Critical/Danger) の 3 段階以上に分類し、表示・音・優先度を差別化する。IEC 62304 Class C デバイスでは UI の安全性も評価対象となる。
- **早期警戒しきい値の設定**: 実際の安全限界より手前に「予警告 (Pre-alarm)」を設けることで、オペレータに対応時間を確保する。
- **冗長警告チャネル**: 主チャネル（画面表示）が機能不全の場合に備え、音響・振動・物理的インジケータなど複数の警告手段を用意する。
- **アラーム疲れ (Alarm Fatigue) の防止**: 不要な警告を抑制し、警告の信頼性を高める。アラームレートの継続的モニタリングと閾値チューニングを行う。
- **タイムスタンプ付きアラームログ**: 警告の発令・確認・対応の記録を残し、事後分析を可能にする。

#### コードレビューチェックリスト
- [ ] 各ハザードシナリオに対して警告発令の条件・タイミング・方法が仕様化されているか
- [ ] 警告発令から安全限界到達までの余裕時間が要件として定義・検証されているか
- [ ] 誤警告率が許容範囲内に管理されているか（閾値と実績データが存在するか）
- [ ] 警告システム自体の障害時（通信断・UI クラッシュ）にもオペレータへの通知が行われるか
- [ ] 警告の優先順位付けロジックが、複数ハザード同時発生時に正しく機能するか

#### 計測指標
| 指標 | 説明 |
|------|------|
| 警告リードタイム | 警告発令から安全限界到達までの平均時間（秒） |
| 誤警告率 (False Positive Rate) | 実際のリスクなしに発令された警告数 / 総発令警告数 × 100 % |
| 警告見落とし率 (False Negative Rate) | 発令されるべき警告が発令されなかった事象数 / 全ハザード事象数 × 100 % |
| 警告応答率 | オペレータが規定時間内に警告に応答した割合（%） |

### 2.5 安全な統合 (Safe Integration)

#### 定義
製品が一つ以上の外部コンポーネント・システムと統合される過程および統合完了後において、安全性を維持できる度合い。統合によって新たなハザードが生じないこと、安全機能が外部の影響を受けて劣化しないことが要件となる。（出典: ISO/IEC 25010:2023 主旨に基づく要約）

#### 調査観点
- 統合する外部コンポーネントの安全性評価（SIL/ASIL/DAL レベルの確認）
- インタフェース仕様（プロトコル・タイミング・エラー処理）の厳密な定義と検証
- 統合後の安全機能のエンド・ツー・エンド検証（結合テスト・システムテスト）
- IEC 61508 Part 1 §7.4 が要求する「サブシステム統合時の安全整合性の維持」
- ISO 26262 Part 9 が要求する ASIL 適合性の分解と再合成

#### 設計タクティクス・パターン
- **インタフェース安全要件仕様 (Interface Safety Requirements Specification)**: 統合インタフェースの安全機能・制約・エラーモードを明示的に定義する。変更管理と合わせてインタフェース凍結プロセスを設ける。
- **入力バリデーションと信頼境界 (Trust Boundary)**: 外部コンポーネントからの入力を信頼しない設計とし、自身の安全要件を満たすバリデーション層を実装する。
- **安全ラッパー (Safety Wrapper)**: 安全認定のない外部コンポーネントをラッパーで包み、安全機能（監視・制限・フォールバック）を付加する。
- **インタフェーステスト・安全統合テスト**: 統合後のシステムに対して FMEA/FTA を再実施し、統合起因の新たなハザードを識別する。DO-178C では統合後の検証を明示的にライフサイクルに含める。
- **バージョン管理と変更影響分析**: 外部コンポーネントのバージョン変更が安全機能に与える影響を、変更管理プロセスで必ず評価する。

#### コードレビューチェックリスト
- [ ] 統合する外部コンポーネントの安全レベル（SIL/ASIL/DAL）が確認・文書化されているか
- [ ] 外部入力のバリデーションが安全機能の内側で実施されているか（外部コンポーネントへの依存がないか）
- [ ] インタフェース仕様の変更が安全影響評価の対象となっているか
- [ ] 統合テストで安全シナリオ（外部コンポーネント障害・異常入力・通信断）が網羅されているか
- [ ] 安全認定外のサードパーティコンポーネントに対して、安全ラッパーまたは同等の対策が施されているか

#### 計測指標
| 指標 | 説明 |
|------|------|
| インタフェース安全要件カバレッジ | テスト済みインタフェース安全要件数 / 定義済みインタフェース安全要件総数 × 100 % |
| 統合起因ハザード数 | 統合テストで新たに識別されたハザード件数（目標: 変更ごとに 0 増） |
| 外部依存 SIL/ASIL 適合率 | 要求 SIL/ASIL を満たした統合コンポーネント数 / 統合コンポーネント総数 × 100 % |

## 3. 横断的設計戦略

### 3.1 安全ライフサイクルの作り込み (Safety Lifecycle Integration)
IEC 61508 は概念→ハザード・リスク分析→安全要件割り当て→設計→実装→検証→運用→廃棄の全フェーズを包括する**安全ライフサイクル**を規定する。安全性はリリース直前の検証フェーズだけでなく、要件定義時から設計に組み込む必要がある（Security by Design と同様の Safety by Design 原則）。

### 3.2 リスクアセスメント手法の組み合わせ
- **HAZOP**: 設計レビュー段階で系統的なハザード洗い出しに使用。
- **FMEA**: コンポーネント単位の故障モードとその影響・重大度・発生確率・検知可能性を分析し、RPN で優先順位付け。
- **FTA**: 特定のトップイベント（安全事故）から演繹的に原因を展開し、定量的な確率計算も可能。
- **STPA**: Leveson（2012）の STAMP に基づく現代的手法。従来の故障モデルでは捉えられない、正常に動作するコンポーネントの組み合わせが引き起こすシステム的ハザードを識別する。複雑なソフトウェア集約システムに特に有効。

### 3.3 安全整合性レベル (SIL / ASIL / DAL) の割り当て
リスクアセスメントの結果に基づき、各安全機能に安全整合性レベルを割り当てる。

| 規格 | レベル体系 | 対象領域 |
|------|-----------|---------|
| IEC 61508 | SIL 1–4（4 が最高） | 産業機械・プロセス制御・汎用 E/E/PE |
| ISO 26262 | QM / ASIL A–D（D が最高） | 自動車 |
| ISO 21448 (SOTIF) | — (リスクベース) | 自動車・自動運転（機能不足リスク） |
| DO-178C | DAL E–A（A が最高） | 航空ソフトウェア |
| IEC 62304 | Class A / B / C（C が最高） | 医療機器ソフトウェア |

割り当てられた SIL/ASIL/DAL に応じて、設計・実装・テスト・ツール検証の各段階で要求される技法と厳格さが決まる。

### 3.4 独立した安全評価と検証
IEC 61508 および ISO 26262 は、SIL 3/4 または ASIL C/D では機能安全アセスメントを**独立した機能安全評価者 (FSAssr)** が実施することを要求する。ソフトウェアの観点では、独立した V&V（検証・妥当性確認）チームの設置、独立したコードレビューとテストが必要となる。

### 3.5 証拠に基づく安全ケース (Safety Case)
安全性を「証明」するのではなく、複数の証拠（ハザード分析・テスト結果・形式的検証・現場実績データ）を積み上げて安全性の主張を支持する**安全ケース**を構築する。Goal Structuring Notation (GSN) または Claims-Arguments-Evidence (CAE) フレームワークで整理することで、監査・認証申請に対応する。

## 5. アンチパターン

| アンチパターン | 問題 | 対策 |
|---------------|------|------|
| **ハザード分析の後付け** | 設計完了後にハザード分析を行っても、根本的なアーキテクチャ変更が困難 | 要件定義フェーズから HAZOP/FMEA/STPA を実施し、安全要件を仕様に組み込む |
| **ウォッチドッグの形骸化** | メインループで機械的にキックするだけでは、ループはまわっているが本来の処理が停止している故障を検知できない | クリティカルな処理パスの完了を条件としたキック設計、またはチャレンジ・レスポンス型ウォッチドッグを採用する |
| **単一の警告チャネル** | 表示系の障害で全警告が届かない | 音響・物理インジケータ等の冗長チャネルを用意する |
| **警告過多 (Alarm Flood)** | 多数の同時警告により重要アラームが埋没、オペレータが麻痺する | 警告の優先度付け・集約・抑制ロジックを実装し、アラームレートを継続的に管理する |
| **外部コンポーネントの無検証統合** | サードパーティライブラリが安全要件を満たすかどうか確認せずに使用 | 統合前に SIL/ASIL/DAL 適合確認を実施し、未評価コンポーネントには安全ラッパーを適用する |
| **安全機能を通常コードと混在** | 安全機能のコードが業務ロジックと混在し、独立した検証が困難 | 安全機能を明確に分離したモジュール・パーティションとして実装する（IEC 61508 の「ソフトウェア分離」要求に対応） |
| **故障注入テストの省略** | フェイルセーフ機構が実際の故障条件下でも動作するかを検証しない | 定期的な故障注入テスト（Fault Injection Testing）を CI/CD パイプラインまたはシステムテストに組み込む |
| **変更時の安全影響評価の省略** | 機能追加・依存更新時に安全機能への影響を評価せずにリリース | 変更管理プロセスに安全影響評価（Safety Impact Analysis）を必須ステップとして組み込む |
