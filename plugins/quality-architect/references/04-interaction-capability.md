# 04. 相互作用性 / Interaction Capability

> このファイルは **ISO/IEC 25010:2023**（第 2 版）に準拠し、旧「使用性 (Usability)」から改称された「相互作用性 (Interaction Capability)」の副特性 8 件を対象とした、調査・アーキテクチャ設計・コードレビュー用リファレンスです。

> **2011 版との違い:**
> - 特性名：Usability（使用性）→ **Interaction Capability（相互作用性）**
> - 副特性：UI 快美性 (UI aesthetics) → **ユーザ従事性 (User engagement)**（機能・情報の提示方法に焦点を拡大）
> - 副特性：アクセシビリティ (Accessibility) → **包摂性 (Inclusivity)** と **ユーザ支援性 (User assistance)** に分割
> - 副特性：**自己記述性 (Self-descriptiveness)** を新規追加

---

## 1. 定義

**相互作用性 (Interaction Capability)** とは、指定されたユーザが、インタラクティブシステムを通じて目標を達成するために必要な対話を行う際の有効性・効率・満足度に関わる特性の総体を指す。2023 年改訂で Usability から改称され、副特性が 6 から **8** に再編された。

- **ISO/IEC 25010:2023**（標準番号: 78176）が Interaction Capability を製品品質モデルの主要特性のひとつとして定義し、8 副特性で構成する。
- **ISO 9241-11:2018** は利用品質の観点から有効性・効率性・満足性の 3 軸を定義しており、相互作用性の測定枠組みと相補的に参照される。

---

## 2. 副特性

### 2.1 適切度認識性 (Appropriateness Recognizability)

**定義**
特定のニーズに対して製品またはシステムが適切かどうかを、ユーザが認識できる程度。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- 初見ユーザが「この製品で自分のニーズが満たせるか」を素早く判断できるか。
- ランディングページ・オンボーディング画面・ヘルプ概要が目的を明示しているか。
- アイコン・ラベル・ナビゲーション構造が機能の意図を視覚的に伝えているか。

**設計タクティクス・パターン**
- ファーストビューに明確な価値提案 (value proposition) を配置する。
- メタファーとアイコンを一貫させ、機能の意図を視覚的に伝える。
- ナビゲーション構造を情報アーキテクチャ (IA) 原則に沿って設計する。
- Nielsen ヒューリスティクス H1（システム状態の可視性）を適用し、現在地・機能の文脈を常に提示する。

**コードレビューチェックリスト**
- [ ] `<title>`・`<meta name="description">` がコンテンツを正確に記述しているか。
- [ ] コンポーネント名・ラベル文言が機能の意図と一致しているか。
- [ ] 入力フォームに placeholder ではなく `<label>` が紐付けられているか。
- [ ] ページ・画面の見出し階層 (`h1`〜`h6`) が論理的に構成されているか。

**計測指標**
- タスク完了前の離脱率 (task abandonment rate)
- 「このツールで目的を達成できそう」と回答する割合（ユーザアンケート）
- ISO/IEC 25023:2016 の Appropriateness recognizability 計測尺度

---

### 2.2 習得性 (Learnability)

**定義**
指定されたユーザが、製品またはシステムを効果的・効率的・安全に使用することを習得できる程度。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- 初回利用からタスク完了に要する時間。
- ドキュメント・チュートリアルなしでも操作できるか（ゼロヘルプ習得性）。
- 複数回使用後の習熟速度（学習曲線の傾き）。

**設計タクティクス・パターン**
- プログレッシブ・ディスクロージャ (progressive disclosure): 初心者には最小機能セットを提示し、習熟に従い高度機能を開示する。
- コンテキストヘルプ・ツールチップ・空状態 (empty state) メッセージで次のアクションを案内する。
- Nielsen の「習得のしやすさ」ヒューリスティクスに沿い、アフォーダンスを明確にする（Nielsen, 1993）。
- ISO 9241-110:2020 の習得性原則を適用し、操作パターンをシステム内で一貫させる。

**コードレビューチェックリスト**
- [ ] 複雑なウィザード・フローに進捗インジケーターが実装されているか。
- [ ] エラーメッセージが原因と回復手順を平易な言語で示しているか。
- [ ] ショートカット・上級機能は UI 上から発見可能か（隠蔽されすぎていないか）。
- [ ] チュートリアルやオンボーディングフローにスキップ手段が用意されているか。

**計測指標**
- 初回タスク完了率・完了時間
- 学習曲線の傾き（セッション数 vs. タスク時間）
- System Usability Scale (SUS) スコア（Brooke, 1996 — Jordan et al. eds., *Usability Evaluation in Industry*, Taylor & Francis）

---

### 2.3 運用操作性 (Operability)

**定義**
製品またはシステムを操作・制御することが容易であり、ユーザが自律的に使用を継続できる程度。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- 日常的な繰り返し操作を最少のステップで実行できるか。
- キーボードショートカット、バルク操作など効率化手段が提供されているか。
- システムへの制御感（undo/redo、キャンセル）が担保されているか。

**設計タクティクス・パターン**
- Nielsen のヒューリスティクス H3（ユーザ制御と自由）および H4（一貫性と標準）を適用する（Nielsen Norman Group 公式）。
- Fitts の法則に基づきインタラクティブターゲットのサイズと距離を最適化する。
- 「元に戻す / やり直す (Undo/Redo)」を一貫して提供する。
- ISO 9241-110:2020 の制御可能性 (Controllability) 原則を設計指針とする。

**コードレビューチェックリスト**
- [ ] フォーム送信・破壊的操作に確認ダイアログまたは Undo が実装されているか。
- [ ] ドラッグ&ドロップなどポインタ操作にキーボード代替が存在するか。
- [ ] API のデフォルト値・プリセットが一般ユースケースを網羅しているか。
- [ ] 長時間処理に進行状況インジケーターとキャンセル手段があるか。

**計測指標**
- タスクあたり操作ステップ数
- エラー回復に要する時間 (mean time to recovery from error)
- ISO/IEC 25023:2016 の Operability 計測尺度

---

### 2.4 ユーザエラー防止性 (User Error Protection)

**定義**
製品またはシステムが、ユーザの誤操作や不正入力が起きにくい構造・仕組みを備えている程度。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- 入力値の制約・バリデーションが事前に明示されているか。
- 取り消し不能な操作の前に十分な警告が行われているか。
- 誤った操作パスを構造的に封じるフローになっているか。

**設計タクティクス・パターン**
- Don Norman の「強制機能 (forcing function)」概念を適用し、誤った操作パスを構造的に封じる（Norman, 2013）。
- フォームはインライン・リアルタイムバリデーションで入力ミスを即時フィードバックする。
- 危険な操作（削除・上書き）には名称入力による確認など、意図的な摩擦を挿入する。
- Nielsen のヒューリスティクス H5（エラー防止）を適用する。

**コードレビューチェックリスト**
- [ ] `<input type="number" min max step>` 等で入力範囲をブラウザレベルで制限しているか。
- [ ] 非同期処理中は重複送信防止 (disable during submit) が実装されているか。
- [ ] エラーメッセージは WCAG 2.2 SC 1.3.3 に準拠し、色だけに依存しないか。
- [ ] API は冪等性 (idempotency) を確保し、重複リクエストを安全に処理するか。
- [ ] 入力フォームは送信前にサマリーレビュー画面を提供しているか（高リスク操作）。

**計測指標**
- タスクあたりエラー発生率
- エラー後の回復成功率
- ISO/IEC 25023:2016 の User error protection 計測尺度

---

### 2.5 ユーザ従事性 (User Engagement)

**定義**
ユーザインタフェースが、機能と情報を誘引的・動機づけ的な方法で提示し、ユーザの継続的な対話を促す程度。旧「UI 快美性 (UI aesthetics)」を置換し、視覚的魅力に加えて動機・関与・継続使用の促進を含む概念に拡張されている。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- ビジュアル階層・余白・タイポグラフィが認知負荷を低減し、快適な体験を促しているか。
- デザインが一貫したビジュアル言語（デザインシステム）を採用しているか。
- インタラクションフィードバック（アニメーション・マイクロインタラクション）が適切に機能しているか。
- ユーザがシステムを使い続けたいと感じるか（継続使用意向）。

**設計タクティクス・パターン**
- デザインシステム（例: Material Design, Apple Human Interface Guidelines）を導入し、一貫性を担保する。
- ゲシュタルト原則（近接・類似・連続）を用いて視覚的グルーピングを設計する。
- ダーク/ライトモード・モーションリダクション等のユーザ設定を尊重する（`prefers-color-scheme`, `prefers-reduced-motion`）。
- O'Brien & Toms (2008) のエンゲージメント要素（挑戦性・新奇性・審美的魅力・フィードバック・インタラクティビティ）を設計指針として参照する。
- ISO 9241-110:2020 のユーザ従事性 (user engagement) 相互作用原則を適用する。

**コードレビューチェックリスト**
- [ ] コンポーネント間でスペーシング・カラートークンが統一されているか。
- [ ] アニメーションに `prefers-reduced-motion` メディアクエリが適用されているか。
- [ ] フォントサイズが相対単位 (rem/em) で指定され、ユーザのブラウザ設定を尊重しているか。
- [ ] コントラスト比が WCAG 2.2 SC 1.4.3（AA: 4.5:1 以上）に適合しているか。
- [ ] マイクロインタラクション（ホバー・フォーカス・ローディング）が一貫して実装されているか。

**計測指標**
- セッション継続時間・リピート訪問率
- User Experience Questionnaire (UEQ) の Attractiveness / Stimulation 因子（Laugwitz et al., 2008）
- ISO/IEC 25023:2016 の User engagement 計測尺度

### 2.6 包摂性 (Inclusivity)

**定義**
年齢・能力・文化・民族・言語・性別・経済状況など、多様な背景を持つ幅広いユーザが製品またはシステムを使用できる程度。旧「アクセシビリティ」から分割され、**障害有無を超えた社会的多様性全体**への対応に焦点を当てる。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- 障害のある人を含む多様なユーザが平等に機能を利用できるか。
- 文化・言語・読解レベルの差異を考慮したコンテンツ設計になっているか。
- 低帯域・低スペックデバイス環境でも基本機能が動作するか。

**設計タクティクス・パターン**
- WCAG 2.2（W3C Recommendation, 2023-10-05）の適合レベル AA を最低基準とし、WCAG 2.1 AA との後方互換性を維持する。
- W3C WAI の「アクセシビリティ・ユーザビリティ・包摂性」フレームワークを設計指針に採用する。
- ユニバーサルデザイン 7 原則（公平な使用・柔軟な使用・単純で直感的な使用など）を適用する。
- 障害当事者・高齢者・多言語ユーザを含むユーザテストを ISO 9241-210:2019 の人間中心設計プロセスに組み込む。
- Focus management を適切に実装し、キーボードのみで全機能を利用可能にする。

**コードレビューチェックリスト**
- [ ] すべての `<img>` に意味のある `alt` テキストが付与されているか（装飾画像は `alt=""`）。
- [ ] フォームコントロールに `<label for>` または `aria-labelledby` が紐付けられているか。
- [ ] フォーカス順序が DOM 順と一致し、可視フォーカスインジケーターが存在するか。
- [ ] 色コントラスト比: 通常テキスト 4.5:1 以上、大テキスト 3:1 以上（WCAG 2.2 SC 1.4.3）。
- [ ] 自動再生メディアに停止・音量制御が存在するか（WCAG 2.2 SC 1.4.2）。
- [ ] タイムアウト処理でユーザへの事前警告と延長手段が実装されているか（WCAG 2.2 SC 2.2.1）。
- [ ] UI テキストが平易な言語（読みやすさレベル）で記述されているか。

**計測指標**
- 自動アクセシビリティ検査ツール（axe, Lighthouse）の違反件数
- スクリーンリーダーによるタスク完了率
- WCAG 2.2 適合レベル（A / AA / AAA）の達成比率
- 多様なユーザプロファイルによる代表的タスク完了率

### 2.7 ユーザ支援性 (User Assistance)

**定義**
製品またはシステムが、最も広い範囲の特性・能力を持つユーザが指定された目標を達成するために必要な支援を提供する程度。旧「アクセシビリティ」から分割され、**支援技術との互換性・補助的サポート機能**に焦点を当てる。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- スクリーンリーダー・スイッチアクセス等の支援技術との互換性が確保されているか。
- ヘルプ・ドキュメント・チュートリアル・ライブサポートへのアクセス手段が適切か。
- 知覚・操作・理解・堅牢性の 4 原則（POUR）への適合度はどうか。

**設計タクティクス・パターン**
- WAI-ARIA 1.2（W3C Recommendation, 2023-06-06）を用いて動的ウィジェットにセマンティクスを付与する。
- WCAG 2.2 の POUR 原則（Perceivable, Operable, Understandable, Robust）を適合基準として採用する。
- ヘルプコンテンツはタスク文脈に即した形（コンテキストヘルプ・インラインヒント）で提供する。
- コールセンター・チャット・FAQ など複数の支援チャネルを用意し、アクセス手段を多様化する。
- WCAG 2.2 SC 3.3.7（冗長な入力の省略）などの新基準を活用し、認知負荷を低減する。

**コードレビューチェックリスト**
- [ ] `role`, `aria-expanded`, `aria-haspopup`, `aria-live` 等の ARIA 属性が正確に使用されているか。
- [ ] 動的コンテンツ更新は `aria-live` リージョンで支援技術に通知されているか。
- [ ] ヘルプ・サポートへのリンクが全ページから一貫した位置でアクセスできるか（WCAG 2.2 SC 3.2.6）。
- [ ] エラー回復のための具体的な修正手順がメッセージ内に含まれているか（WCAG 2.2 SC 3.3.3）。
- [ ] キーボードトラップが発生していないか（WCAG 2.2 SC 2.1.2）。

**計測指標**
- 支援技術ユーザによるタスク完了率・完了時間
- WCAG 2.2 SC 別適合率（特に新規追加の SC 2.5.7, 2.5.8, 3.2.6, 3.3.7, 3.3.8 等）
- ヘルプリソースへのアクセス頻度・解決率

### 2.8 自己記述性 (Self-Descriptiveness)

**定義**
製品が、ユーザが必要とする場所において適切な情報を提示し、製品の機能と使用方法をユーザが過剰な操作や外部リソース（ユーザドキュメント・ヘルプデスク等）を参照することなく即座に把握できる程度。ISO/IEC 25010:2023 で新規追加された副特性。（ISO/IEC 25010:2023 に基づく要約）

**調査観点**
- ユーザが次に何をすべきかが画面内の情報だけで分かるか。
- システムの状態・機能・操作手順がコンテキストに応じて適切に表示されているか。
- ヘルプなしで機能の目的と操作方法が理解できるか。

**設計タクティクス・パターン**
- ISO 9241-110:2020 の「自己記述性」相互作用原則（7 原則のひとつ）を適用する：ダイアログの現在地・実行可能な操作・実行方法を常に明示する。
- Nielsen のヒューリスティクス H1（システム状態の可視性）・H6（認識 vs. 想起）を適用する。
- 空状態・ゼロデータ状態・初期状態に必ずガイダンスメッセージを配置する。
- ツールチップ・プレースホルダー・インラインラベルを使い、各コントロールの目的を自明にする。
- パンくずリスト・ステップインジケーター等でユーザの現在位置を常に可視化する。

**コードレビューチェックリスト**
- [ ] 各ページ・画面にユーザの現在地を示すナビゲーション要素（パンくず・見出し等）があるか。
- [ ] 空状態・エラー状態・読み込み状態に説明テキストとアクション提案が含まれているか。
- [ ] ボタン・リンクのラベルが「クリック」ではなく具体的なアクションを示しているか（例：「送信」→「レポートを送信」）。
- [ ] フォームフィールドの期待する入力形式・例示が `placeholder` または説明文で提供されているか。
- [ ] 非自明なアイコンにはテキストラベルまたはツールチップが付与されているか。
- [ ] ショートカットキー・ジェスチャー操作の一覧が画面内または即座にアクセスできるヘルプに記載されているか。

**計測指標**
- ドキュメント・ヘルプ参照なしのタスク完了率（ゼロヘルプ完了率）
- ユーザが「次に何をすべきか分かる」と回答する割合（タスクベースアンケート）
- SUS スコアの「このシステムを使いやすいと感じた」項目スコア
- ISO/IEC 25023:2016 の Self-descriptiveness 計測尺度

## 3. 横断的設計戦略

### 3.1 人間中心設計プロセスの採用
ISO 9241-210:2019 は、利用状況の理解 → ユーザ要件の明確化 → 設計案の作成 → 評価 の反復サイクルを定義する。相互作用性品質はこのプロセスを製品ライフサイクル全体に組み込むことで継続的に向上する。障害当事者・高齢者・多文化ユーザを含むユーザテストを各サイクルに組み込む。

### 3.2 ユーザビリティテストの計画的実施
Nielsen (1993) は 5 名程度の参加者でユーザビリティ問題の約 85% を発見できることを示した。スプリントごとの小規模テストを推奨する。多様なユーザプロファイルを対象に定期的にテストを実施する。

### 3.3 ヒューリスティック評価
Nielsen の 10 ヒューリスティクス（Nielsen Norman Group 公式、1994 公開・2024 改訂）はコストの低い専門家評価手法として広く適用される。特に H6「認識 vs. 想起」は自己記述性に、H7「柔軟性と効率」は運用操作性に直結する。

### 3.4 デザインシステムとコンポーネント駆動開発
コンポーネントライブラリへのアクセシビリティ・一貫性・自己記述性の組み込みにより、個別実装の品質ばらつきを抑制する。デザイントークン（カラー・スペーシング・タイポグラフィ）を単一のソースで管理する。

### 3.5 継続的アクセシビリティ・包摂性監査
CI パイプラインへの自動アクセシビリティ検査（axe-core 等）の組み込みにより、退行を早期検出する。定期的な手動評価と支援技術ユーザによるテストを組み合わせる。

### 3.6 ISO 9241-110:2020 相互作用原則の適用
7 つの相互作用原則（適切性・自己記述性・ユーザ期待への準拠・習得性・制御可能性・エラー頑健性・ユーザ従事性）を設計レビューのチェックリストとして活用する。

---

## 4. レビュー時の重点チェックリスト（要約）

| 副特性 | 最重要確認事項 |
|--------|---------------|
| 適切度認識性 | 価値提案が初見で伝わるか、`<title>` / `<meta>` が正確か |
| 習得性 | 初回タスク完了率、エラーメッセージに回復手順があるか |
| 運用操作性 | Undo/Redo の一貫性、キーボード代替の有無 |
| ユーザエラー防止性 | バリデーション、破壊的操作の確認フロー、冪等性 |
| ユーザ従事性 | コントラスト比 AA 適合、デザイントークン一貫性、`prefers-reduced-motion` 対応 |
| 包摂性 | WCAG 2.2 AA 適合、多様なユーザでのテスト実施、平易な言語 |
| ユーザ支援性 | ARIA 正確性、フォーカス管理、ヘルプアクセス一貫性 |
| 自己記述性 | 空状態ガイダンス、具体的ボタンラベル、現在地の可視化 |

## 5. アンチパターン

| アンチパターン | 問題 | 対策 |
|--------------|------|------|
| **Dark Pattern** | 解約・キャンセルを意図的に困難にする | 操作の可逆性を設計原則として明文化する（運用操作性・ユーザエラー防止性） |
| **エラーコードのみ表示** | `Error: 0x80004005` では回復不可能 | 平易な言語と回復手順を必ず付記する（自己記述性・習得性） |
| **色のみによる情報伝達** | 色覚多様性のあるユーザが情報を取得できない | 形・アイコン・テキストを組み合わせる（WCAG 1.4.1）（包摂性） |
| **過剰な確認ダイアログ** | 全操作に確認を求めると警告疲れを招く | 破壊的・取り消し不能な操作に限定する（ユーザエラー防止性） |
| **アクセシビリティ後付け** | リリース直前の対応では修正コストが急増 | 設計初期から POUR 原則・包摂性を組み込む（包摂性・ユーザ支援性） |
| **モバイル未考慮のフォーカス管理** | モーダル開閉後にフォーカスが迷子になる | 開閉ごとに `focus()` を適切に移動させる（ユーザ支援性） |
| **アイコンのみ UI** | アイコンの意味がユーザに伝わらない | テキストラベルまたはツールチップを必ず付与する（自己記述性） |
| **低エンゲージメント設計** | 視覚的魅力・フィードバックの欠如でユーザが離脱 | マイクロインタラクションとデザインシステムで一貫した体験を構築（ユーザ従事性） |
