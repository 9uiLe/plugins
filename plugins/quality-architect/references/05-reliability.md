# 05. 信頼性 / Reliability

> ISO/IEC 25010 製品品質モデルの「信頼性」に関する、調査・アーキテクチャ設計・コードレビュー用リファレンス。

---

## 1. 定義

**信頼性 (Reliability)** とは、ISO/IEC 25010 が定める品質特性であり、特定の条件下・期間においてシステム・製品・コンポーネントが意図した機能をどれだけ安定して果たせるかを示す。  
障害の発生頻度・継続時間・影響範囲を最小化し、稼働継続性と回復能力を兼ね備えることが品質目標となる。

Avizienis ら（2004）は *dependability*（信頼可能性）を包括的概念として定義し、その属性として **reliability**（連続稼働の確率的尺度）・**availability**（稼働準備度）・**safety**・**integrity**・**maintainability** を分類した。ISO/IEC 25010 の信頼性特性はこの枠組みと整合する。

---

## 2. 副特性

### 2.1 成熟性 (Maturity)

> **2023 改訂での変更:** ISO/IEC 25010:2023 では「成熟性 (Maturity)」が **欠陥のなさ (Faultlessness)** に名称変更された。概念は「通常運用において欠陥なく機能を遂行できる度合い」としてより明確に定義し直されている。

#### 定義
通常運用条件下において、システムが信頼性に関するニーズを満たす度合い。障害頻度の低さと、意図せぬ動作の少なさで表される。

#### 調査観点
- 過去の障害履歴・障害率の推移
- テストカバレッジ（命令・分岐・変異テスト）
- KLOC あたりの既知欠陥密度
- 本番リリース前の平均障害間隔

#### 設計タクティクス・パターン
- **ソフトウェア信頼性成長モデル (SRGM)**: Musa–Okumoto 対数ポアソン・モデルや Goel–Okumoto モデルを用い、リリース可否の定量判断に使用する。
- **継続的テスト**: 単体・統合・回帰テストを CI/CD パイプラインに組み込み、欠陥の早期検出を実現する。
- **段階的ロールアウト (Canary / Blue-Green)**: 本番障害の影響範囲をコントロールしながら成熟度を漸進的に高める。

#### コードレビューチェックリスト
- [ ] 例外・エラーパスに対する単体テストが存在するか
- [ ] NULL・境界値・異常入力を含むテストケースが含まれているか
- [ ] 変異テスト (mutation testing) による欠陥検出率が目標値を超えているか
- [ ] 依存ライブラリに既知の重大 CVE が存在しないか

#### 計測指標
| 指標 | 式 |
|------|----|
| 欠陥密度 | DD = 検出欠陥数 / KLOC |
| 障害率 λ(t) | SRGM により推定（例: Goel–Okumoto: λ(t) = a·b·e^{-bt}） |
| テストカバレッジ | C = カバーされた分岐数 / 全分岐数 × 100 % |

### 2.2 可用性 (Availability)

#### 定義
必要なときにシステムが稼働・アクセス可能な状態にある能力の度合い。稼働時間の割合で定量化される。

#### 調査観点
- SLA で定義されたダウンタイム上限と実績値の乖離
- 計画外停止の頻度と継続時間
- デプロイ・メンテナンス時のサービス継続策（無停止デプロイ等）

#### 設計タクティクス・パターン
- **冗長化 (Redundancy)**: アクティブ–アクティブ / アクティブ–パッシブ構成で単一障害点 (SPOF) を排除する。
- **ヘルスチェックと自動フェイルオーバー**: ロードバランサーとオーケストレーター（Kubernetes 等）による障害ノードの自動排除。
- **ローリング / カナリアデプロイ**: デプロイ時の稼働率を維持する。
- **Error Budget**: Google SRE モデルでは (1 − 可用性目標) を誤りに充当できる予算とし、信頼性と開発速度のトレードオフを定量管理する。

#### コードレビューチェックリスト
- [ ] ヘルスチェックエンドポイント（/health, /readiness, /liveness）が実装されているか
- [ ] データベース接続プールの上限とタイムアウトが明示されているか
- [ ] デプロイスクリプトにゼロダウンタイム戦略が含まれているか
- [ ] 依存サービス障害時にサービス全体が停止しない設計か

#### 計測指標
| 指標 | 式 |
|------|----|
| 可用性 A | A = MTBF / (MTBF + MTTR) |
| MTBF | MTBF = 総稼働時間 / 障害発生回数 |
| MTTR | MTTR = 総復旧時間 / 障害発生回数 |
| 年間許容ダウンタイム (99.9%) | ≒ 8.76 時間/年 |
| 年間許容ダウンタイム (99.99%) | ≒ 52.6 分/年 |

### 2.3 障害許容性・耐故障性 (Fault Tolerance)

#### 定義
ハードウェアやソフトウェアに何らかの欠陥が生じても、システムが本来の振る舞いを維持し続けられる能力の度合い。Avizienis ら（2004）の障害–エラー–故障連鎖モデル（fault → error → failure）における「エラーの伝播をシステム障害に至る前に遮断する」能力に対応する。

#### 調査観点
- カスケード障害（連鎖障害）が発生し得る依存グラフの特定
- 依存サービスの障害時の自システムの挙動
- リトライ・タイムアウト・バックオフ戦略の有無

#### 設計タクティクス・パターン
- **サーキットブレーカー (Circuit Breaker)**: Nygard（2018）が体系化。障害閾値に達した下流サービスへの呼び出しを遮断し、高速フェイルにより資源枯渇を防ぐ。Closed / Open / Half-Open の 3 状態遷移で動作する。
- **バルクヘッド (Bulkhead)**: スレッドプール・接続プールをサービスごとに分離し、障害の影響範囲を隔壁 (bulkhead) で封じ込める。
- **タイムアウト (Timeout)**: 応答待機の上限を設け、資源を枯渇させない。すべての外部 I/O に必須。
- **リトライ + 指数バックオフ + ジッター**: 一時的障害を吸収しつつ、過負荷を増幅させない。
- **フォールバック (Fallback)**: 障害時にデグレード応答（キャッシュ値・デフォルト値）を返すことでサービスを維持する。
- **カオスエンジニアリング**: Basiri ら（2016）が提案。障害を意図的に注入し、耐故障性を検証する実験的手法。Netflix Chaos Monkey が先駆的実装。

#### コードレビューチェックリスト
- [ ] すべての外部サービス呼び出しにタイムアウトが設定されているか
- [ ] サーキットブレーカーが適切な閾値・回復待機時間で設定されているか
- [ ] リトライに上限回数・バックオフ・ジッターが含まれているか
- [ ] 障害時にカスケードが発生しない設計か（bulkhead の確認）
- [ ] フォールバックのデグレードレスポンスが定義されているか

#### 計測指標
| 指標 | 説明 |
|------|------|
| 障害伝播率 | 下流障害に起因した自サービス障害件数 / 下流障害件数 |
| サーキットブレーカー Open 率 | 観測期間中に Open 状態であった割合 |
| リトライ成功率 | 1 回以上リトライで成功したリクエスト / 全リトライ発生リクエスト |

### 2.4 回復性 (Recoverability)

#### 定義
障害や中断が生じた際に、影響を受けたデータを取り戻し、システムを正常な稼働状態へ戻すことができる能力の度合い。

#### 調査観点
- RTO（Recovery Time Objective）・RPO（Recovery Point Objective）の定義と実績
- バックアップ戦略（頻度・保持期間・オフサイト保管）
- 障害復旧手順書の整備と定期的な訓練（Disaster Recovery Drill）

#### 設計タクティクス・パターン
- **チェックポイント (Checkpointing)**: 定期的にシステム状態を永続化し、障害後の再開点とする。
- **WAL (Write-Ahead Log) / ジャーナリング**: データベースのトランザクションログにより、クラッシュ後でも ACID 性を保証して回復する。
- **冪等性 (Idempotency)**: リトライによる重複操作を排除し、回復処理を安全に再実行可能にする。
- **Saga パターン**: マイクロサービス間の分散トランザクションを補償トランザクションで回復する。
- **Runbook 自動化**: 障害対応手順を自動スクリプト化し、MTTR を短縮する。

#### コードレビューチェックリスト
- [ ] RTO / RPO が非機能要件として文書化されているか
- [ ] バックアップの取得・リストア手順がコードまたは IaC で管理されているか
- [ ] 分散トランザクションに補償ロジックまたは冪等キーが実装されているか
- [ ] ロールバック手順が定義され、定期的にテストされているか

#### 計測指標
| 指標 | 式 |
|------|----|
| MTTR | MTTR = Σ復旧時間 / 障害件数 |
| RTO 達成率 | RTO 以内に復旧した件数 / 全障害件数 × 100 % |
| RPO 達成率 | 最大データ損失量が RPO 以内であった件数 / 全障害件数 × 100 % |

## 3. 横断的な設計戦略

### 3.1 観測可能性 (Observability) の確立
障害の早期検出と MTTR 短縮には、**メトリクス・ログ・トレース**（三本柱）の整備が前提となる。Google SRE では Four Golden Signals（レイテンシ・トラフィック・エラー率・飽和度）による監視を推奨する。

### 3.2 Error Budget によるリリース管理
Google SRE モデルでは、可用性目標（例: 99.9%）を超えた障害発生時はリリースを凍結し、信頼性向上作業に集中する。開発速度と信頼性のトレードオフを定量的に管理するプラクティスである。

### 3.3 防御的プログラミングと Design by Contract
- 事前条件・事後条件・不変条件を明示し、契約違反を早期に検出する。
- Fail-Fast 原則: 不正状態を検知したら即座に例外を送出し、エラーの伝播を防止する。

### 3.4 依存性の管理
- 外部依存を最小化し、各依存に対して SLA・タイムアウト・フォールバックを定義する。
- 非同期メッセージキュー（Kafka 等）を用いた疎結合アーキテクチャにより、依存先の障害が即時伝播しない設計とする。

### 3.5 カオスエンジニアリングの継続実施
本番環境またはステージング環境で計画的に障害を注入し（Chaos Monkey / Chaos Toolkit 等）、信頼性設計の仮定が実際に成立するかを検証する。実験は仮説→計測→比較の科学的手順で実施する（Basiri et al., 2016）。

## 5. アンチパターン

| アンチパターン | 問題 | 対策 |
|---------------|------|------|
| **タイムアウト未設定** | 応答待機によるスレッド枯渇とカスケード障害 | 全外部 I/O に接続・読み取りタイムアウトを設定 |
| **無限リトライ** | 障害中の再試行がサービスに過負荷を与える | 上限回数・指数バックオフ・サーキットブレーカーで制御 |
| **単一障害点 (SPOF)** | 1 コンポーネントの障害がシステム全体を停止させる | 冗長化・フェイルオーバーで SPOF を排除 |
| **ヘルスチェック未実装** | 障害ノードにトラフィックが継続ルーティングされる | /readiness・/liveness エンドポイントを実装 |
| **バックアップ未検証** | バックアップが存在しても復元不能な場合がある | 定期的なリストア訓練 (DR Drill) を実施 |
| **モノリシック障害ドメイン** | 一部の障害が全機能を停止させる | バルクヘッドによる障害ドメインの分離 |
| **グレースフルデグレード欠如** | 依存サービス障害時に即座に全機能停止 | フォールバックとデグレードレスポンスを設計 |
