ADR-0042クライアント状態管理ライブラリの選定

フロントエンドの状態管理を Redux から段階的に移行する。サーバー状態とクライアント状態を分離し、軽量で型安全なライブラリ構成を採用する。

Context

現行のフロント (React 18 / 約 38 万行) は 2019 年に導入した Redux + redux-saga を基盤としている。プロダクトの成長に伴い、以下の問題が顕在化している。

現状の問題

  • ボイラープレートが過剰 — Action / Reducer / Saga を 1 機能あたり平均 4 ファイル書く必要があり、新規開発のリードタイムが遅延。
  • サーバー状態とクライアント状態の混在 — API レスポンスのキャッシュを Redux で管理しているため、再フェッチ・無効化ロジックが各 Saga に散らばっている。
  • 型推論の弱さ — connect() 経由の props は型推論が浅く、リファクタ時の安全性が低い。
  • バンドルサイズ — redux + saga + reselect で初期バンドルに 62 kB (gzip) を占有。

Decision Drivers

  1. 段階移行可能であること — 既存 Redux を一気に置き換えるのは現実的でない。共存できること。
  2. サーバー状態を専用ライブラリで扱える — クエリキャッシュ・再フェッチ・楽観的更新をフレームワーク化したい。
  3. 型安全 — TypeScript 5.x で strict モードに耐える型推論。
  4. バンドル増分が最小 — 移行完了時にネット −30 kB 以上を達成する。
  5. 学習コスト — オンボーディング 1 日以内で書ける API 面積。

ベンチマーク (10k items, 100 selectors, re-render 計測)

Tested on M1 Pro / Chrome 125 / 100 回平均。Option D は再レンダリング暴発のため参考値。

Decision

✓

Decision

Option B を採用する。クライアント状態には Zustand、サーバー状態には TanStack Query (旧 React Query) を導入し、責務を明確に分離する。既存 Redux は strangler fig パターンで機能単位に段階的に置換する。

採用理由

  • クライアント状態とサーバー状態を別ライブラリで扱うことで、各々のベストプラクティスを採用できる。
  • Zustand は ~1.2 kB と最軽量。API も create 1 関数のみで学習コストが低い。
  • TanStack Query はキャッシュ・無効化・楽観的更新・SSR 対応を標準提供。Saga で書いていたボイラープレートの大半が消える。
  • Redux Toolkit (Option A) は移行先としては優秀だが、根本的な「ボイラープレート過多」「サーバー状態の混在」を構造的には解消できない。

Migration Plan

i

移行方針

Big-bang 移行は避け、機能単位 (cart, search, profile, ...) で段階置換する。両ライブラリは feature flag で共存可能。

作業ステップ

  1. Setup — zustand / @tanstack/react-query の導入、ESLint ルール追加、テンプレート整備。
  2. 規約策定 — store 命名規則 (use<Domain>Store)、クエリキー設計 ([domain, action, params]) を README にまとめる。
  3. Greenfield — 新機能は B のみで実装。3 ヶ月でドッグフード。
  4. 機能単位の置換 — cart → search → profile → settings の順で migration PR を作成。
  5. Cleanup — Redux 残骸の削除、最終ベンチマーク、本 ADR の更新 (Status: Accepted → Implemented)。

Consequences

Before / After

Before · 現行 Redux

  • 機能あたり 412 行のコード
  • Redux 関連で 62 kB 占有
  • サーバー状態のキャッシュ自前実装
  • connect() の型推論が弱い
  • P75 リードタイム 4.2 日
→

After · Zustand + TanStack Query

  • 機能あたり 140 行 (推定 −66%)
  • 追加 14 kB / 削除 62 kB = ネット −48 kB
  • キャッシュは TanStack Query が標準提供
  • 完全な型推論 (strict 対応)
  • P75 リードタイム目標 2.5 日

Positive

  • 新規機能の実装速度が 30–40% 向上する見込み。
  • サーバー状態の 無効化バグ (現状 P0/P1 の主因の 1 つ) が構造的に減少。
  • バンドルサイズの純減により、モバイル LCP が改善。

Negative / Risks

!

既知のリスク

  • 移行期間中の二重メンテナンス — Redux と Zustand が共存するため、共有状態のシンクが必要なケースが発生する。
  • SSR の挙動差 — Next.js での hydration に注意。store は client-only で初期化する。
  • devtools の劣化 — Redux DevTools のような時間旅行は Zustand では限定的。

Neutral

  • チーム内の Redux 知見はミドルウェア層 (auth, telemetry) でしばらく活用できる。
  • TanStack Query の staleTime / cacheTime 設計について、ドメインごとの規約を別途決める必要がある。

Compliance & Monitoring

本 ADR の遵守は CI で自動チェックする。

★

Success Criteria

  • 2027-Q1 終了時点で Redux の総 import 件数が 0 になること。
  • 本番バンドル (gzip) が −30 kB 以上削減されていること。
  • 機能リリースの P75 リードタイムが 3 日以内に短縮されていること。
